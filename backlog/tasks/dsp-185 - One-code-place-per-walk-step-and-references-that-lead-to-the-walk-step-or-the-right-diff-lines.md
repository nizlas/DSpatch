## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Niclas's evaluation of 0.1.11, 9 November 2026 (points 2 and the navigation side of 4).

- The basic rule is one code place per walk step, with its own explanation for that place; the walk's step order binds the reasoning together. Observed: one step with three places (declaring a build option; passing a choice on as a compiler definition; wiring in an optional dependency) where Next place kept the same shared text, leaving the reader to match text to code. These should be three steps whose explanations build on each other.
- Several places in one step only when necessary for understanding and the presentation really helps the reader compare them: a justified teaching exception, not a formatting variant. Places that need their own explanation and are visited in turn are separate steps.
- Implemented in walk generation and its structural checks, keeping coverage and valid references. Saved walks are not changed destructively and still open; new or explicitly regenerated walks follow the rule. A profile switch never changes a walk's structure, order, places or coverage.
- References to code inside the walk lead first to the walk step and its explanation. Necessary references outside the walk are clickable and open the right file, diff page and section of the diff view with the lines marked. Structured references where possible; no jump to a guessed place; an unresolvable reference, or code not in the current diff, says so plainly. File and line references are allowed where needed, and then they navigate.

Extension (Niclas, 9 November 2026, before the final verification and release):
- **A separate pane per code place, also within one file.** Reviewing one file, a single file view was reused and scrolled up and down while stepping, which loses the context and makes horizontal navigation with Shift + mouse drag hard. The file name alone must not decide a pane's identity or merge places. Next/previous activates and shows the corresponding pane in the horizontal view, not vertical jumps between sections of a shared file pane; each pane keeps its position and view context when going back and forth; Shift + mouse drag works also when the drag starts over the code. Pane reuse and mouse interaction are investigated as separate possible causes and both verified in a real window. This concerns the presentation of places; separate steps with their own explanation remain the rule.
- **A walk follows the important connections into new implementation.** A code walk is a coherent path through the change's important connections; that a part may be in another walk is not enough if the reader loses the connection here. The generator judges new or substantially changed called functions that are central to what the walk explains: if the implementation is needed to understand the main course, it gets its own step in the right place in the reasoning; if it is a relevant side deepening, there is a clear clickable reference. Not every call is followed mechanically: the choice is motivated by understanding, behaviour and relevant risks, not call order; a self-explanatory function name is not enough reason to skip important new implementation. Facts are checked in the code (e.g. a started service is not assumed connected or initialised because its start function returned). No extra step with the same caller code only as transport between two function visits: the caller's pane stays as orientation and the explanation makes a short transition; the same place is revisited only with a new, meaningful explanatory purpose.
- **References can be followed and returned from.** Implementation treated in another walk: link to the concrete walk step when it is the right deepening, with an easy way back to the original place; if central here too it may have a focused step in this walk (overlap between walks is no reason to leave out a needed explanation). A necessary side reference without a fitting step opens the right section of the Gerrit-style diff view at the right revision, diff page and lines, visibly marked; a target that cannot be found says so, with no guess. No redundant file names and line numbers in prose for code the walk shows.
- **Profiles keep their level.** Better coverage comes from a considered step sequence, not from packing every implementation into each explanation. Essentials about two natural sentences; Standard the connections and mechanisms that add understanding; Teacher its accepted scope; no profile retells statements or repeats comments; a profile switch keeps the walk's structure and places.
- Verified on a synthetic case of the same structure: a caller with two meaningful new functions, several places in one file and a relevant side reference. No workplace code in public tests or product instructions.
- Quality correction (Niclas, 9 November 2026): a step held three pieces of code and two were treated in passing; even Teacher reduced an acquire function with a mutex, a shared pointer, a flag and a condition variable to "get-or-create" and "safe to repeat". A code place is not treated because it is in the step or its function is named: every central mechanism is explained at the chosen profile's level, and the three places would normally be steps of their own. Teacher identifies the concepts and connections needed to review the code — e.g. which shared state a lock protects and which other paths or threads use the same lock; why lookup and creation must be protected together; a scoped lock's lifetime and automatic release; what shared ownership means for ownership and lifetime, and that shared ownership does not make the contents thread-safe; how a new request, its flag, the notification and the waiting loop that receives it connect; the difference between reusing an object, creating a request and the work actually having been done. The agent uses the shared read access to read the relevant types, callers, accesses to the state and the waiting/working code at the review's revision before writing, and does not guess the architecture from names. Where relevant code really is missing, Teacher still explains the general concepts and keeps them apart from what cannot be established about this implementation; missing context leads neither to invented connections nor to skipped concepts. Purpose and interplay in connected reasoning — not line-by-line paraphrase or a general language lesson; Teacher takes the room understanding needs; Essentials stays short. A synthetic quality case with a producer/worker relation and shared ownership is judged on whether the explanation makes the relation understandable; containing the words is not a test.

## Implementation Notes
<!-- SECTION:NOTES:BEGIN -->
Implementation, 9 November 2026 (uncommitted working tree on 9ea512b; status stays In Progress until independent verification and review).

**Walk generation (AC #1).** `PLACE_RULES` in `app/src/shared/review-agent.ts` is a new "## One place per step" section of `walksPrompt`: one code place per step with its own explanation, the order carrying the reasoning, places visited in turn as separate steps (option declared, passed on, used: three steps), From and To of one change as one place, several places only as a justified exception with a per-step `"together"` reason in the answer schema. `crowdedStepProblems` (structural only: `distinctPlaceCount` pairs base/target of the same file, context places not counted) adds each step with more than one place and no reason to the existing single repair round in `prepareWalks` (`app/src/host/review-agent-jobs.ts`); `repairPrompt` then says how to split. Never a second round: a step still crowded after it is kept as written (no place or coverage lost) and `crowdedNote` says so in the job note and the walk's provenance. Coverage and place/reference checks are unchanged. A profile still never changes structure (`walkExplanationSection` unchanged).

**Model (AC #2).** `WalkStep.together?` (`review-model.ts`), parsed in v2 when present, written by `definitionFrom`, counted in `stepContentHash` only when present, so saved steps keep their hash (a test pins a pre-DSP-185 hash). Step shows "Shown together: …" (`data-ev="step-together"`) above the places list when a step has several. Saved walks with several places open as before.

**References (AC #3).** `app/src/shared/reference-links.ts` resolves structurally, never by text: a checked line reference whose path and side match a walk place and overlaps its focus leads to that step and place (the narrowest containing focus first, then the largest overlap; the step being read, then walk order, among equals); otherwise a file the diff changes opens at those lines in the walk window's code view with `rv-ref-mark` rows (the existing `goAway`/`openLocation` path, verified to mark exactly the lines); a file the diff does not change opens the same way and is labelled "not in this diff: unchanged code at this revision". Explicit step references `{"label", "step": "W1.2"}` are read from the references block (`readStepAnswer`, `stepReferencesFrom`), stored on discussion answers and step explanations, and resolved against the walk shown; an unknown id or no open walk is text with the reason (`data-ev="answer-ref-unresolved"`), never a link. Unchecked references stay under "What DSpatch did not accept". Rendering is in one place, `DiscussionAnswer.tsx` (`ReferenceItem`, `ReferenceLinksContext`), used by Step explanations and Discussion answers; following a step link offers "Back to <step>" (`data-ev="step-link-back"`). The walk outline sent with step explanations now carries step ids, and `STEP_REFERENCE_RULE` tells the explanation prompt to point at other steps by id. The profile instruction version stays 4 (the reference format, not a profile's manner, changed).

**Simulator (AC #4).** `presentation-review-tasks.ts`: a called function's definition is its own step after the call (`from` the call); the default scenario adds exactly one comparison step with a `together` reason; simulated step explanations add one step reference and one diff reference outside the walk. `DSPATCH_REVIEW_SIM=crowded` / `crowded-once` exercise the repair path; `threads` and `bad-ref-first` are unchanged in structure.

**Trials.** `thread-trial.mjs` was stale since DSP-184 at "Explain this from the explanation": it now expects Explain this from Step in Step (the selection shown with an explain-this explanation) and no discussion question (counted from the saved record). `profile-trial.mjs` gained a stage: the explanation's references are "This step", a step link to W1.3 and a diff link; the step link goes to W1.3 with its place marked and Back returns; the diff link opens `src/app.js` in the walk window with exactly the referenced lines marked.

**Extension (A–E and the quality correction), same day.**
- *Panes (AC #5).* Two possible causes were examined apart. (1) Pane reuse: `panesOf` (`app/src/renderer/walk-panes.ts`) merged any neighbouring station of the same file whose change areas (hunks ± 3 lines) overlapped, so close places of one file shared one pane that scrolled. Now a station joins the previous pane only as the other side of the same change (the pane holds one station, at the other side, overlapping hunks); otherwise every place has its own pane. Nothing else keys panes by path (pane identity is its index; each keeps its own scroll memory). (2) Mouse: Shift + left drag starting over code text was tried in a real window on Linux (Xvfb, xdotool) plainly, over an existing text selection, and with the keyboard focus in the docked panel, with and without a `preventDefault` guard on the press: it panned in every case, so no mouse fault was reproduced and the guard was not kept. `ReviewTimeline.tsx` is unchanged.
- *Coherent path (AC #6).* `PATH_RULES` ("## A coherent path" in the walk prompt): central new or substantially changed called functions get a step at the right point or a followable reference, chosen by understanding, behaviour and risk, not call order; a self-explanatory name is no reason to skip; overlap with another walk is no reason to leave out; facts checked in the code (a returned start is not a connected service); no transport-only revisit of the caller. Schema field `revisit` (what is new at a place shown again); `repeatedStepProblems` sends a step that exactly repeats an earlier place of its walk with no `revisit` into the same single repair round; still unresolved, it is kept and `repeatedNote` says so. `revisit` is stored (`WalkStep.revisit?`, hashed only when present) and shown as "Shown again: …".
- *References across walks (AC #7).* The walk outline sent with step explanations (`walkOutlineOf`, one builder for the window and scripts) also names the review's other walks with step ids; `STEP_REFERENCE_RULE` allows ids of other walks; `resolveStepReference` already searched every walk. A followed step link, also into another walk, offers "Back to <step>"; a diff reference opens the walk window's code view at its file and lines, marked, and Back restores the walk position. Side references open in the walk window's own diff view when a walk window is open (the existing routing); with no walk window they open in the diff window.
- *Quality correction (AC #8), profile instructions v5.* `MECHANISM_RULES` in every generation path (walk generation through `walkExplanationSection`, present and regenerate through the base rules, more, simpler and explain through the reader line): code is treated only by explaining its central mechanisms at the profile's level; read the types, callers, other accesses to the same state and the waiting or working code before writing, without inferring architecture from names; with code missing, explain the general concepts and say what cannot be established. Teacher's manner adds how to find the concepts a reviewer needs (shared state and who else touches it, what must happen together, ownership and lifetime and what shared ownership does not guarantee, hand-offs and how the receiver learns of them, reused vs requested vs done), in connected reasoning, no line-by-line paraphrase or language lesson, taking the room understanding needs. `PLACE_RULES` in the walk prompt says the same of steps. `PRESENTATION_INSTRUCTION_VERSION` is 5.
- *Synthetic cases.* `app/tests/support/synthetic-walks.ts`: `WORKER_CASE` (a caller calling `startWorker()` and `subscribeToPairs(items, n)`, both added further down the same file within the old shared change area, and a second file as another walk) and `WORK_QUEUE_CASE` (a mutex-protected map of `std::shared_ptr<Job>` slots, `acquire` under a `lock_guard` setting `pending` and notifying, a worker loop waiting on the condition variable, and a caller) with a three-step walk. The simulator follows a same-file call to a function defined in another changed range in call order (`callOrder`), reached from the call; simulated explanations also link a step of another walk. `app/scripts/explain-prompt.mjs` writes the exact Essentials/Standard/Teacher prompts DSpatch sends for a chosen step of the work-queue case (through `stepExplanationPrompt`, now the channel's own prompt builder) and copies the revision folder they name, for an independent qualitative check.
- *What the simulated provider proves.* Structure (steps, places, panes, repair round), prompt content and the UI and data flow. Whether a real model chooses the central implementations well, writes a coherent path, or makes the producer/worker relation understandable in each profile needs Niclas's judgement of real generated walks and explanations; no test checks for keywords in an answer.
