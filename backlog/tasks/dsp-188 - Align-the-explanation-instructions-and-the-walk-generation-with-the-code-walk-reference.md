## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Follow-up to Niclas's adoption of docs/CODE_WALK_UNDERSTANDING_AND_PROFILES.md (9 November 2026). The reference defines code understanding, the walk's pedagogical flow and the explanation profiles. DSP-184, DSP-185 and DSP-186, decided the same day from his evaluation of 0.1.11, implemented parts of it: step explanations apart from the discussion, no instruction text in the reading flow, one code place per step with its own pane, central new functions as steps, references that lead to the step, and reviews as instances. Read against the code on main at 0.1.12 (`app/src/shared/presentation-profiles.ts` at instruction version 6, `app/src/shared/review-agent.ts`), these differences remain:

- Essentials is instructed to write "two plain, natural sentences" and to "name at most one or two identifiers", and Standard gets "about four to six sentences"; the reference wants no sentence quota and no identifier limit in any profile (sections 4 and 6) and lets the scope follow the step.
- The instruction set has grown into several rule lists (same facts, grounding, explanatory value, mechanisms, length, deepening, walk-relative writing, and per-profile manners of up to nine items); the reference asks for a shared task, a short addition per profile and the technical contract, at its own level of abstraction, with relevant exceptions inside the principle rather than stacked rules, and warns that overloaded instructions make explanations worse (section 6). The mechanism rules list what to cover; the reference keeps investigation scope apart from explanation scope (section 3).
- The walk generator says how a hop connects to the one before and gives central new functions their own step, but nothing about alternative branches as alternative paths that return to the branch point, workers and callbacks with the execution context being followed, or a teaching order that says when it differs from the execution order (section 1).
- External context: the reference wants its meaning explained and the source opened in the code view with its revision stated, never pasted into the reading flow, with version uncertainty stated once where it changes a conclusion (section 8); whether the current explanations and references do this has not been checked against it.
- Verification: 0.1.12 judged model-written answers on a synthetic example outside DSpatch's providers; the reference asks for all three profiles on several synthetic cases from the final request path, presented with their context, and for Niclas's judgment on real code (section 11).

The change is to the derived instructions and the product, not to the reference. Keep the agent's freedom to choose how to explain, and judge the result on actually generated explanations, not on type checks or prompt strings; a documentation change proves no better pedagogy. The decided behaviours of DSP-180, DSP-181 and DSP-184 to DSP-186 that the reference keeps (saved choice, the settle delay, latest-step-wins, late answers, cache, explicit retry, no call on opening, step explanations in Step, review instances) stand.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
9 November 2026, Windows, main checkout. Governing decisions: docs/CODE_WALK_UNDERSTANDING_AND_PROFILES.md sections 1 (transitions, teaching order), 3 (investigation scope apart from explanation scope), 4 (no quotas), 6 (shared task, short profile addition, technical contract apart), 8 (external context), 11 (verify on generated text); VISION.md 1.14; the decided behaviours of DSP-180 to DSP-186 kept.

**Path investigated.** A step explanation is built in the window: the review service's envelope for the step (focus lines, counterparts, the diff section), the revision folder section from the analysis host, the walk outline and `stepExplanationPrompt` (src/main/step-explanation-channel.ts, src/shared/review-discussion.ts). Walks are prepared on the host from `walksPrompt` (src/shared/review-agent.ts) over the whole change, all steps in one JSON answer. Explain this (`selectionPrompt`) sends the exact selection with the lines around it and the change section. Why Explain this read better at 0.1.12: one focused task over one piece of code, with the surrounding lines and read tools, against stacked rule lists with sentence and identifier quotas for the step explanation; and walk bodies written once for every step together, with no instruction about how a step connects to a branch, a worker or a callback.

**Changed.** `src/shared/presentation-profiles.ts` at instruction version 7: one `EXPLANATION_TASK` for every profile (what the code does here and why it matters for the change, how it connects to what the reader has seen and will see, what the reader must understand to judge it; read the code it rests on first; add understanding beyond the lines; keep what the code shows apart from interpretation; scope follows the code and the reader, no length to hit, no required form), `SAME_FACTS_RULES` kept, a short `reader` text per profile instead of `manner`/`guideline`/`details` lists, `DEEPENING_RULES` for the text after the marker (continues the first part rather than restating it; the comparison with the earlier revision once), `WALK_READING_RULES` for writing relative to the walk and making a transition comprehensible (reached from and what the caller needs; a return; an alternative outcome back at the branch point; a worker or callback with what starts it and which execution context follows; a teaching order that differs says so; what an earlier step established is recalled in a line, not derived again; what follows from the language's rules is a fact, what depends on timing or callers is what the code allows). Removed: GROUNDING_RULES, EXPLANATORY_VALUE_RULES, MECHANISM_RULES, LENGTH_GUIDELINE_RULES, WALK_WRITING_RULES and every sentence or identifier count. The technical contract (marker, references block, JSON shapes) is unchanged and kept apart. `src/shared/review-agent.ts`: FORM_RULES gained the branch, worker/callback and teaching-order rules as judgment; PLACE_RULES says every central mechanism a step shows is explained in that step; the summary hints lost their counts. The simulated provider's prompt headings are unchanged, so every existing window trial still keys on them.

**Tooling.** `tests/support/synthetic-walks.ts` gained CONNECT_CASE and `connectWalk()` (TypeScript: a connection with retries, two outcomes and a callback deferred through setTimeout). `tests/support/explain-prompts.ts` and `scripts/explain-prompt.mjs` build the exact prompts for either case: a step in every profile, Explain this on a line range (`--selection path:start-end`), and the walk generation prompt (`--walks --profile`); the script replaces an earlier read-only copy of the revisions. Tests updated to version 7 (explain-prompts, presentation-profiles, presentation-walks, presentation-chain, review-discussion-service); the sentence-count assertions in presentation-chain were replaced by the profiles differing.

**Checks on Windows (this revision).** `npm run typecheck` clean. `node scripts/run-tests.mjs review`: 318 pass, 1 fail, the fail being `tests/review-context.test.ts:352` (the test joins a path with the platform separator and compares it with a forward-slash read log; it fails on Windows before this change too and is unrelated). The presentation group passed after the instruction rewrite; the later changes touch only review-group tests.

**Generated texts (outside DSpatch's providers).** No real provider is usable on this machine (the Copilot account lists no models; the Claude provider is not installed), so Claude subagents stood in for the review agent and answered DSpatch's exact prompts with read-only access to the revision folders the prompts name: for the work-queue case (C++) W1.2 `acquire()` in Essentials, Standard and Teacher, W1.3 `workerLoop()` in Standard, and Explain this on lines 14–24; for the connect case (TypeScript) W1.2 `connect()` in all three profiles, W1.3 `settle()` in Standard, Explain this on lines 17–30, and the whole walk generation in Standard. Two rounds: a second model judged the first round's eleven texts against the code (every claim and reference range), then three sentences of the instructions were adjusted (above) and the step texts and the walk were generated again with the final instructions; the Explain this prompt is the same in both rounds. The texts, their code and the judgment are in app/release/profile-examples-0.1.13.md (not in Git), given to Niclas. They are not evidence of how his provider behaves on real code; that judgment is his.

**What the texts show.** No claim wrong about what the code does in either round (the judge and my own check against the files); every reference range correct. Every step text says what the code does here, why it matters for the change and what the reviewer must weigh; the transition to the worker thread ("This step changes thread"; "a wake-up, not a hand-over") and to the deferred callback (microtask before timer task, so `'retrying later'` is reported before `'offline mode'`) is made comprehensible; alternative outcomes are handled as alternatives (connected / gave-up / a rejection that reaches neither; a wake-up caught or lost at start-up); the code's guarantees are stated exactly (the lock covers only the accesses under it, the notification keeps no memory, the specified order is a rule, scheduling-dependent paths are what the code allows). Teacher differs in kind (concepts built at the point of use, an analogy, a concrete `runs` example); Essentials and Standard differ in density. Explain this on the same lines gives the better ordered trace of what the lines do; the step text gives the better framing of what to decide. The generated walk read through DSpatch's own `readWalksAnswer`, `walkPlaceProblems`, `crowdedStepProblems` and `repeatedStepProblems` with no problems: three walks (the transport opens; giving up after every attempt fails; the transport rejects), 13 steps with 15 places and 9 from-links, alternative outcomes as walks of their own that return to the branch point ("Back at the branch: open is false"), the deferred callback followed into the timer's turn ("startSession resumes first; 'session ready' arrives afterwards"), a rejection as the path that reaches neither outcome, a later step recalling an earlier one instead of deriving it again, and `why` carrying the judgment ("The user is promised a retry that this change does not implement"). The structural checks forced none of this; the first round's walk had 18 steps in the same three shapes.

**Remaining weaknesses (for Niclas's evaluation).** (1) Repetition between the part shown at once and Show more is reduced in the second round (the comparison with the base revision is made once, Essentials' deepening halved) but not gone: a deepening paragraph still tends to restate its bullet before adding. (2) The first part is long for the profile in the complex case: about 270 words for Essentials, 300–410 for Standard and 450–650 for Teacher on the work queue; the simple connect case gets 150 words in Essentials. (3) Essentials and Standard converge after the marker. (4) Fixed phrases: "Two/Three things decide…", and the hedge "what the code allows, not something observed" once per text. (5) Small precision slips in the first round (a reversed order in Explain this's short answer, a right conclusion with a wrong reason) show that a sharp reader is still needed. (6) Not covered by the synthetic cases: external context, a shared snapshot, a simple setting; the judgment of real-model text on real code remains Niclas's.

**AC 3 (external context).** The product opens a context reference at its recorded commit in the code view and pastes nothing of the context into the prompt or the reading flow (DSP-175, `tests/review-context.test.ts`); the instructions ask for meaning in the text and references for the source. Whether a generated explanation conveys external context well was not judged in this round, since neither synthetic case has any; recorded as not established, not as verified.
