## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
### Why this matters

Maestro is the product's own orchestration: DSpatch running a defined agent loop for the user, rather than the external loop we use to build DSpatch. The two are separate and must stay so — one is how we work, the other is something we ship.

This story exists because the work was previously buried inside [DSP-15](dsp-15%20-%20Agree-the-next-direction-for-review-and-Maestro.md), a discovery and decision story that depends on the whole review-research chain. Defining and running an agent loop does not need an HCI literature review, and Niclas raised the mismatch on 15 September 2026. Splitting it removes an invented dependency and lets the two proceed at their own pace.

### Reshaped on 15 September 2026, when Niclas chose this direction

He decided to build the loop and edit it in a graph editor shaped like [the reference figure](../../docs/assets/agentloop_generisk.png). That split this story's original content three ways, and **this card is now the runner**:

- [DSP-21](dsp-21%20-%20Define-the-agent-loop-graph-format.md) settles the graph format, which is the contract and the only shared prerequisite.
- [DSP-22](dsp-22%20-%20Build-a-graph-editor-for-agent-loops.md) builds the editor, which can proceed in parallel because it is unaffected by how runtime faults are handled.
- This story executes a graph for real and reports what happened.

A hand-written graph from DSP-21 is enough to build against; this does not wait for the editor.

### Scope

Run **one** bounded loop for real, from a graph. Not a configurable orchestration framework, not every workflow the vision imagines, and not the full Maestro of [VISION.md](../../docs/VISION.md#14-implementation-phases). One loop, defined well enough that a reader knows where it stops, executed on a real task in a real repository with a real build or test.

Our own external development loop is the nearest evidence we have about what works, including its failures: a specialist call that never reported back and blocked the loop for six hours, reports lost because a role could not write them, and reconciliation after an interrupted call. Use that experience rather than repeating it.

**The written design already exists and is not this story.** [DSP-9](dsp-9%20-%20Dokumentera-Maestros-egen-orkestrering.md) delivered [docs/MAESTRO_ORCHESTRATION.md](../../docs/MAESTRO_ORCHESTRATION.md), 216 lines covering architecture, delegation, state and recovery, providers' internal subagents, a cost model per loop step and attempt, useful implementation increments, and what a prototype must demonstrate. It is in Review awaiting Niclas's judgement, and it is the same material DSP-15 calls "the Maestro proposal in PR #7". Start from section 11, *What a prototype must demonstrate*, and section 10's increments. Where this story departs from that document, say so and why; a written vision is discussion material, not a specification that must be implemented as drawn.

### The constraint that keeps this honest

Delegating more work raises, not lowers, what must remain understandable. The point of the review work is to make delegated work inspectable; an orchestration whose output nobody can review would defeat it. Criterion #3 carries that requirement, and it is deliberately the hardest one here. Splitting this story from DSP-15 separates the work, not the obligation.

### Relationship to DSP-15 and the milestone

Deliberately **not** dependent on DSP-14 or DSP-15, and deliberately outside milestone m-1, which is discovery. [DSP-15](dsp-15%20-%20Agree-the-next-direction-for-review-and-Maestro.md) remains where Niclas chooses the next direction between review features and orchestration; this story is what gets built if orchestration is chosen, and it can be planned before that choice. If Niclas prioritises it ahead of DSP-15, record that as the direction decision rather than leaving DSP-15 to claim a choice that was already made.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 One bounded loop is expressed as a graph in the shared format, and the runner executes that graph rather than a hard-coded sequence. What the agent may do without asking, where it must stop and what the user sees while it runs are stated, and departures from the external development loop and from the orchestration vision are explained rather than inherited.
- [x] #6 The declared failure edges are honoured, not just drawn: a failure the loop classifies routes where the graph says, and the run records which edge it took and why. A runtime fault such as a hung or undelivered call is handled by the runner, is never mistaken for a declared failure, and leaves a record a person can act on.
- [x] #2 The loop runs end to end on a real bounded task in a real repository, producing an actual code change and a real build or test run. The run is recorded, and a failed or abandoned run is reported as such.
- [x] #3 Everything the loop did is inspectable afterwards and bound to an identified revision: goal, attempts, changed files, commands run, results and decisions. An agent narrative alone does not satisfy this criterion.
- [ ] #4 Human-interactive work stays available throughout. Autonomy can be switched off mid-run without losing context or history, and switching it off neither resets files nor replays completed work.
- [x] #5 Step, time and cost limits are enforced, and the behaviour on reaching a limit is demonstrated rather than assumed. Duration and usage are measured and reported; missing measurements are recorded as unknown.
