## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Niclas's assignment of 10 November 2026: a first, bounded agent loop for generating new code walks inside the product, as an optional evaluation mode beside today's single-call generation, so that what the loop adds can be seen. DSP-188 keeps its own status and its pending human judgment.

**Governing decisions.** docs/CODE_WALK_UNDERSTANDING_AND_PROFILES.md governs the pedagogy (sections 1–4 for what a walk and a step are, 6 for how instructions are derived, 9–10 for state, 11 for verification); docs/AGENT_BEHAVIOUR_AND_ORCHESTRATION.md section 1 (the role decides the method, the graph the steps and routes, the engine the execution; everything DSpatch adds is explicit and inspectable) and section 5 (orchestration and review share the agent connection; an agent's acceptance never becomes human approval); docs/MAESTRO_ORCHESTRATION.md sections 3, 6 and 8 (Maestro owns the flow, registers work before starting it, records cost per step with unknown as unknown); docs/INTERACTION_MODEL.md section 1 and 4.5 (cancel preserves what was done); VISION.md section 3.4 (a walk is never an approval; the agent does not change code; reviews are instances; step explanations belong to Step) and 3.3 (review uses the same agent connection).

**What is built.** Three roles, planner, writer and reviewer, as agent nodes of a DSpatch loop graph (`docs/loop/graphs/dspatch-walk-loop.graph.json`, roles in `docs/loop/roles/review/`), walked by the existing run engine (`runLoopGraph`: routing on declared outcomes, the rework bound, the journal) with a step executor for review work: one read-only analysis session per role over the two revisions, through the provider and model the person chose for walk preparation. The planner reads the revision and plans the walks (purpose, steps, places, transitions); the writer explains each step in the chosen profile, with the whole plan and its own reading of the code, one step at a time in its own session; the reviewer judges the finished walk against the code and the reference's criteria and either accepts it or names concrete shortcomings. One targeted correction round at most: structural findings go to the planner (and the affected steps are rewritten), explanation findings to the writer (only the named steps); the reviewer then gives a final assessment that starts no further round and reports what remains. Today's generation stays as the default and the comparison path; both write the same walk definition format, so the walks open and read the same.

**Traceability and state.** The run's plan, draft, findings, corrections and final assessment are kept as run artefacts of the review (a run record in the loop's record format, and the engine's result store), with provider, model, graph version, role versions, every prompt and answer, times and the usage the provider reported (unknown where it reported none). The job line shows what the loop is doing and can stop it; a provider failure or an interruption ends the job without any automatic retry; a late answer never reaches another review or recreates a deleted one; Step and Discussion are untouched. The trace is readable on request and never in the normal reading flow. The reviewer's assessment approves no code, changes no human decision and resolves no finding.

**Verification.** Routing, the bound, the prompts, the readers, cancellation, failure and state with automated tests and a real window trial with the simulated provider; a comparison of today's generation and the loop on the same code, profile and model over varied generic cases, judged on understanding rather than counts; the comparison through the real product path with a real provider where one is available, or the exact statement of why it was not possible. Simulated trials and subagents outside DSpatch are not evidence of the product path's model quality; Niclas's judgment on real code remains open.

**What the run engine already gave, and what was added.** Used as they are: `runLoopGraph` (src/shared/loop-run.ts: routing on declared outcomes and failures, `delivers`/`consumes` for what a step is handed, the `maxReworkRounds` bound with `routeLimitAs`, the journal, the result store), the graph format and loader (`loadLoopGraph`, `parseLoopGraph`, `checkLoopGraph`), role sources resolved by `createFileRoleResolver` from DSpatch's own resources (the repository or the bundled copy, which the app bundle and the host package already carry under docs/loop), the run record format and writer (`RunRecordWriter`, `parseRunRecord`), the analysis adapter and its policy check (`ReviewAgentJobs.openSession`), the revision snapshot, the walk readers and checks (`readWalksAnswer`, `walkPlaceProblems`, `crowdedStepProblems`, `repeatedStepProblems`, the one repair turn, `definitionFrom`), the job record and its guards. Added at the engine's injection point: a step executor for review work (src/host/walk-loop-run.ts), since the live executor (`createLiveExecutor`) makes one provider turn per node and works in a project's working roots with snapshots and gates, while the walk loop needs several turns inside the writer's step, read-only analysis sessions in the revision folder and no working-copy snapshots. Real gaps found and left as they are: no per-step model choice (the drawing says `inherit`; the person's one choice is used for all three roles); no per-turn token figures in the record format (the executor keeps what the adapter's `usage` events report and writes `unknown` otherwise; the presentation adapter reports nothing); no resume of an interrupted run (as for every loop run). One validator change: a node whose role must not write files may leave a `stored-result`, because the runner binds the body the step returned and writes no file; the error stays for a Markdown file such a node would have to write itself (`loop-graph-load.ts`, tests/loop-graph.test.ts).

**The drawing and the roles.** docs/loop/graphs/dspatch-walk-loop.graph.json: `plan` (outcomes planned, replanned; failure blocked → stopped) → `write` (written) → `review` (accepted → delivered; rework-plan → plan with the findings delivered; rework-text → write with the plan and the findings; objections → delivered-with-objections; limit-reached → delivered-with-objections). `maxReworkRounds` 1 on the review node is the one round; `maxCalls` 7 lets the sixth call route on its own verdict. Target label claude-code; roles walk-planner, walk-writer, walk-reviewer in docs/loop/roles/review/, each `no-file-writes, no-subagent-delegation`, each derived from the reference at its level (purpose, responsibilities, boundaries, delivery; no quotas, no mandatory disposition). The prompts (src/shared/walk-loop.ts) reuse the walk generation's FORM, PLACE and PATH rules for the planner, the shared `EXPLANATION_TASK`, `SAME_FACTS_RULES`, the profile's reader and `WALK_READING_RULES` for the writer (instruction version 7, the same as a step explanation), and give the reviewer the reader and six questions drawn from the reference's sections 1 to 4 with the rule that style is no finding, that a statement about the code that is not true is a finding whatever its size (added after the first evaluation round, below), and that different good explanations are accepted. The planner answers the walks' JSON without bodies and with a brief per step; the writer answers one step's Markdown with the details marker; the reviewer answers JSON with a verdict and findings of kind structure or explanation. The executor derives the node outcome from the reviewer's JSON (any structural finding → rework-plan, else rework-text; on the second visit rework reads as objections); a step is written again only when a finding names it or its places, context places included, changed in a replan (matched by signature, so unchanged steps keep their text whatever their new id).

**State and the window.** `AgentJobRequestInput.method` and `AgentJob.method` (single, the default, or loop); `AgentJob.loop` carries the summary (`WalkLoopSummary`); `ReviewGeneration.method` records how the review's walks were last prepared. The record and `summary.json` sit in `userData/reviews/generated/<review>/<job>.walk-loop/`, removed with the review's artefacts on delete. The picker (`AgentPicker`, `pair-walks-agent-method`) offers the choice; the computer's last choice is kept like the default profile. The job line names the loop and shows each role's activity. `WalkLoopTrace` in the diff window (data-ev `pair-walk-loop`) shows one closed line and, opened, the reviewer's verdicts and findings, the engine's journal and every prompt and answer whole through `reviewPair.walkLoopRecord`. Nothing of it reaches Step or Discussion. Cancel aborts the engine's signal and cancels the active role session; a turn that fails or is cancelled ends the job as before, a cancel between steps ends it as cancelled; `accepts` guards the definition write; a deleted review gets nothing back.

**Simulated provider.** src/main/presentation-review-tasks.ts answers plan-walks, write-step and review-walks (accept; `DSPATCH_REVIEW_SIM=loop-rework` asks once for the first step and leaves one objection; `loop-replan` sends a structural finding and then accepts).

**Changes after the first evaluation round.** (1) A defect the loop found: the planner's context places (DSP-175) were kept in the delivered definition but not shown to the writer and the reviewer, and a changed context place did not count as a changed step; the reviewer's structural finding in the context case was exactly that. Fixed (`placeLines` renders reviewed and context places together in every role's prompt; `stepSignature` includes context places; a test covers it). (2) The reviewer's instruction, in the role and the prompt: a statement about the code that is not true is a shortcoming whatever its size; acceptance requires nothing false. (3) One orientation sentence in the writer's step section (the places are shown beside the text; name functions, not paths). After these, connect and context were run again: in both the reviewer requested one correction round with concrete true findings (connect: two; context: three, among them a comment line the text said was not there and a false rule about the regular expression), the writer rewrote exactly the named steps in its session, and the final assessment verified the corrections and accepted. The first drafts and the final texts stand side by side in the materials.

**Remaining weaknesses, for Niclas's judgment.** The loop's texts repeat an argument across steps (the lock discipline up to eight times in work-queue) and put hypotheticals into first parts where Show more would serve; the reviewer did not flag that, and the writer's instruction asks for it only in a sentence. Whether the sharpened reviewer causes rework on trivia on other code is not established (every finding in these runs was a real error). The wait is real: with a provider the planner and the writer's one call per step will dominate; measured only with the stand-in. The first-round planner left the rejecting transport to a Show more where the one call made a walk; the second run planned the walk. The prompts' place format (one side per place) was found awkward by every stand-in beside the rule that From and To of one change are one place; unchanged here, it predates this task. Nothing here is evidence of what Niclas's provider writes on real code; AC 5 stays open for that.
