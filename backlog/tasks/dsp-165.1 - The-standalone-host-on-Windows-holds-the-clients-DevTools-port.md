## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in DSP-165's Windows verification (3 November 2026): after the client that started the local standalone host ended, its DevTools port stayed bound until the host ended. Suspected: the host inherits a listening socket handle when it is started. Only the debugging port's behaviour has been observed.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 The cause is established by reproduction, told apart from a lingering client process and from a debugger the host starts through inherited arguments or environment
- [x] #2 The host is started so that it holds none of the client's debugging resources, by a bounded change in the process start
- [x] #3 Verified on Windows with an isolated profile: the client's debug port is free once the client has ended while the host lives, work goes on, the client reopens on the same host with no second start and no lost history, and the host's own port, ownership and logging still work
- [x] #4 A focused regression test where it is practical

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Result (3 November 2026, Windows 11, run from the repository).

Cause, by reproduction with a minimal Electron client outside DSpatch: a client with --remote-debugging-port started a detached child as ensureLocalHost did (Node spawn) and quit. The client had ended and no process of its profile was left except the child, yet the port stayed LISTENING with the ended client as its owner, and was freed the moment the child ended. The child had no debugging argument, no inspector and no debugging environment variable (only ELECTRON_RUN_AS_NODE and CHROME_CRASHPAD_PIPE_NAME). So the host inherited the client's listening socket handle: Node starts children on Windows with handle inheritance on, and Chromium's DevTools socket is inheritable. Not a lingering client process, and not a debugger of the host's own.

Fix (local-host.ts, Windows only): the host is started through PowerShell's Start-Process, which goes through ShellExecute and hands the new process none of the caller's handles while keeping its environment; cmd redirects the host's output to host.log as before. A start that cannot be quoted for cmd (a path with a double quote or %) falls back to the old spawn. Without an exit code, a host gone with no claim for 3 s counts as failed; each start passes its host a token (DSPATCH_HOST_START_TOKEN, recorded as startedBy in host-running.json) so a starter whose own host lost the race waits for it to end before returning, and no late loser can take the folder after the winner ends. POSIX starts are unchanged.

Verified with real Copilot, isolated profile, disposable project, npm run dev with DevTools port 9500: the host started as electron.exe under a cmd started through the shell, with its pipe claim and its log; a 50 s command was started and the client closed: all client processes ended, port 9500 free, the host alive and listening on its own port, the command still running; the client reopened on port 9500 again (no bind error), attached to the same host (one start in the log), and the job had finished once while it was closed, with its reply and history. Automated: a Windows regression test with a real Electron client and DevTools port (Node's start holds the port, the new start does not, the child alive in both), the local-host tests three times with no leftover host, fast 1465 and host 107.

Limits: only the DevTools socket was observed; whether other inheritable client handles reached the host before is not established, and the fix covers them only because ShellExecute passes none. The host still inherits the client's environment, including CHROME_CRASHPAD_PIPE_NAME, with no effect observed. Starting through PowerShell adds about a second to a host start on Windows. POSIX is unchanged and was not tried.
