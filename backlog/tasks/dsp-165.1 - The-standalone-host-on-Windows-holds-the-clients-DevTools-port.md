## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found in DSP-165's Windows verification (3 November 2026): after the client that started the local standalone host ended, its DevTools port stayed bound until the host ended. Suspected: the host inherits a listening socket handle when it is started. Only the debugging port's behaviour has been observed.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 The cause is established by reproduction, told apart from a lingering client process and from a debugger the host starts through inherited arguments or environment
- [x] #2 The host is started so that it holds none of the client's debugging resources, by a bounded change in the process start
- [x] #3 Verified on Windows with an isolated profile: the client's debug port is free once the client has ended while the host lives, work goes on, the client reopens on the same host with no second start and no lost history, and the host's own port, ownership and logging still work
- [x] #4 A focused regression test where it is practical

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Result (3 November 2026, Windows 11, run from the repository).

Cause, by reproduction with a minimal Electron client outside DSpatch: a client with --remote-debugging-port started a detached child as ensureLocalHost did (Node spawn) and quit. The client had ended and no process of its profile was left except the child, yet the port stayed LISTENING with the ended client as its owner, and was freed the moment the child ended. The child had no debugging argument, no inspector and no debugging environment variable (only ELECTRON_RUN_AS_NODE and CHROME_CRASHPAD_PIPE_NAME). So the host inherited the client's listening socket handle: Node starts children on Windows with handle inheritance on, and Chromium's DevTools socket is inheritable. Not a lingering client process, and not a debugger of the host's own.

Fix (local-host.ts, Windows only): the host is started through PowerShell's Start-Process, which goes through ShellExecute and hands the new process none of the caller's handles while keeping its environment; cmd redirects the host's output to host.log as before. A start that cannot be quoted for cmd (a path with a double quote or %) falls back to the old spawn. Without an exit code, a host gone with no claim for 3 s counts as failed; each start passes its host a token (DSPATCH_HOST_START_TOKEN, recorded as startedBy in host-running.json) so a starter whose own host lost the race waits for it to end before returning, and no late loser can take the folder after the winner ends. POSIX starts are unchanged.

Verified with real Copilot, isolated profile, disposable project, npm run dev with DevTools port 9500: the host started as electron.exe under a cmd started through the shell, with its pipe claim and its log; a 50 s command was started and the client closed: all client processes ended, port 9500 free, the host alive and listening on its own port, the command still running; the client reopened on port 9500 again (no bind error), attached to the same host (one start in the log), and the job had finished once while it was closed, with its reply and history. Automated: a Windows regression test with a real Electron client and DevTools port (Node's start holds the port, the new start does not, the child alive in both), the local-host tests three times with no leftover host, fast 1465 and host 107.

Limits: only the DevTools socket was observed; whether other inheritable client handles reached the host before is not established, and the fix covers them only because ShellExecute passes none. The host still inherits the client's environment, including CHROME_CRASHPAD_PIPE_NAME, with no effect observed. Starting through PowerShell adds about a second to a host start on Windows. POSIX is unchanged and was not tried.

Current focus (3 November 2026, Niclas's request before push): remove the fallback to Node's spawn for paths windowsHostStart would not quote, since it brings the socket inheritance back; and test whether the 3 s limit or the start bound can report a start as failed while its host later starts and takes the folder.

Follow-up before push (3 November 2026, Niclas's request).

1. The fallback to Node's spawn is gone. It was taken for any value with `"`, `%`, CR or LF; of valid Windows paths only `%` reaches it (a folder named `100%`), and that start then inherited the client's handles again. Two cases also passed unguarded: `!` in a folder name where the registry turns on delayed expansion, and an argument ending in a backslash, which the program reads as an escaped quote. Now every path and argument goes to the start as an environment variable, and the PowerShell script and cmd line are fixed text naming them; cmd expands each once and does not read the result again, `/v:off` stops `!`, and a trailing backslash is doubled for the program's own reading. A value with a double quote, NUL or line break, which no Windows path holds, is refused with a sentence rather than started another way.

2. The 3 s limit was not the defect, but timing showed two:
- A start slower than its bound was reported as failed while its host went on, and 12 s later that host owned the folder with nobody attached. Now this start's own host (and on Windows the cmd running it) is stopped and waited for before the failure is reported; another starter's is left alone. POSIX spawn had the same gap and gets the same stop.
- With several slow starts at once, every start but one was reported as "ended before it was ready" although the winner became ready. Root cause: cmd's `>>` cannot open a file another cmd holds, so each later start's cmd ended before running its host (two cmds appending to one file: the second's output never arrived). The host now writes host.log itself with a shared append (`--log`), and cmd writes only to a file of its own start (`host-start-<token>.log`, cleared on later starts once nothing holds it), which keeps what a host prints before its logging is open. The 3 s limit applies only to a start whose own process has ended with no claim, so a slow start is never cut by it.

Checks run (Windows): a whole-chain test with folder names holding space, `100%`, `%PATH%`, `&`, `^`, `!`, `'`, `()`, `[]`, `;,=`, `åäö` and an argument ending in `\`: the program got exactly its arguments and working folder, and its output reached the log; the DevTools test with the shell start in a folder named `devtools 100% a&b ^!(x) åäö`; timing tests: four slow starters at once all get the one host, two starts slower than a 2 s bound are stopped and no host owns the folder 9 s later, a failing start is reported within 10 s with the file holding what it printed; local-host, ssh-connection and host-data tests (55 pass, 2 skipped), no process left. Real window with real Copilot, profile in `…\dsp win 100% a&b ^!(x) åäö\profile`: host as electron.exe with its arguments intact and its own log; a 40 s command running, client closed: port 9520 free, host alive on its own port, command running; reopened on 9520 with no bind error, same host (one start), the job completed once with its reply.

Earlier results that still stand: the cause by reproduction, the first real-Copilot close/reopen on port 9500, fast 1465 and host 107 (before this follow-up).

Incident: a first attempt passed the special profile path through `npm run dev --`; npm on Windows runs the script through cmd, which mangled the argument, and Electron fell back to Niclas's real profile (%APPDATA%\DSpatch). That window started a standalone host over the real data folder at 23:01; it adopted nothing (no older host folder exists), touched no conversation, and was stopped within minutes. Left in the real profile: host.log (4 lines from that host), remote-token (new), host-claim.json and host-running.json (stale, not held: the pipe is gone), an empty host-start-*.log, and Electron's own Session/Preferences updates. The verification was rerun with `node scripts/dev.mjs` directly. Paths that cmd would act on cannot be passed to npm run dev on Windows; that is npm's shell, not DSpatch's start.

Limits: POSIX starts were changed only in stopping their own late host (spawn kill on the bound) and were not run here. Only the DevTools socket was observed as inherited. Starting through PowerShell adds about a second on Windows. The remote Windows start over SSH still redirects with cmd's `>>` to host.log; whether concurrent remote starts hit the same sharing failure was not tried.

Current focus (3 November 2026): a guard in the verification start that checks Electron's chosen userData against the intended isolated profile before any host starts, connects or profile data is written; and the remote Windows start over SSH, which still redirects with cmd >> host.log.

Second follow-up (3 November 2026, before push).

1. Profile guard (commit edd58b1). `node scripts/dev.mjs --isolated-profile <folder>` passes the folder to Electron as an argument with no shell and sets DSPATCH_EXPECT_USERDATA; the main process compares it with the profile Electron chose first thing, before the single-instance lock writes into the profile and before any host starts or connects, and exits with 25 on a mismatch or when --user-data-dir is missing. dev.mjs stops before starting anything when --isolated-profile has no folder or comes with --user-data-dir. Checked on Windows: a profile in `dsp guard 100% a&b ^!(x) åäö\profile` was accepted and the host started there; Electron given disposable folder A while B was expected exited 25, A stayed empty, B was never created, no host started; the two dev.mjs refusals started nothing. Unit tests (tests/profile-guard.test.ts, fast group). The guard was not exercised against the real profile, as instructed, so the missing --user-data-dir case is covered by the unit test only. The files the earlier incident left in Niclas's real profile were left alone.

2. Remote Windows start over SSH (commit a2881ad). Confirmed with the real start script in real PowerShell, a home of its own, and an installed launcher that waits 3–4 s before the real host: three starts at once all answered started=yes and one host owned the folder, but only one start reached the host program; the other two cmds ended before running it (cmd's >> cannot open a file another cmd holds) and their refusals never reached the log. A host failing at its start was reported only after the full 180 s, with no log lines. Fixed with the local start's solution: the host logs itself (--log), cmd writes only to its own start's file, and a created process that has ended with no live claim for 3 s is reported as failed=start with the last lines of that file and host.log. After the fix: all three starts reached the host program with the expected arguments, two refusals and one "serving" in host.log, one host, stopped cleanly; a failing start answered in about 4 s with what it printed. Tests in tests/ssh-connection.test.ts (Windows suite). The SSH transport itself is not verified: no SSH host running Windows was available, so the script ran locally in PowerShell, not through ssh.

Still to verify on Linux, not covered by any Windows test: the POSIX process identity in the remote steps (DSP-164: identity recorded and checked through /proc, Replace refusing an unconfirmed process), and the local start stopping its own late host when the start bound passes (spawn path, SIGKILL of the child). Both are unchanged-on-Windows paths; nothing here was run on Linux.

Remaining limits: the remote Windows start still runs the launcher through cmd with paths written into the command line, so a data folder whose path holds `%` could be misread there (not tried); the local Windows start passes paths as data. Only the DevTools socket was observed as inherited.
