## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Niclas's assignment of 10 November 2026, after running 0.1.14 with the planner, writer and reviewer: a coherent improvement of the walk preparation's user interface. Two observed faults in the diff (Gerrit) view, and a run view of its own for following the loop. Presentation, observation of the run and the state of a profile switch only: no new pedagogical prompt changes. DSP-188 and DSP-189 keep their pending human judgment.

**Observed.** After preparing with the loop in Standard and switching the reading profile to Essentials, the diff view showed a mass of text above the file list: *Prepared through the planner, writer and reviewer loop: delivered, one correction round …* followed by hundreds of token values in what looked like a closed details line, and beside it *The code walks of this review were prepared with earlier settings (the standard profile). Prepare them again …*.

**Root causes (established in the code).** (1) `WalkLoopTrace` in `PairReview.tsx` wrote every usage reading the provider reported into the `<summary>` line of its details element, joined by commas. A real provider reports usage per model call (Copilot's `assistant.usage` is one event per LLM API call with input and output tokens; Claude reports four fields per turn), so a loop run with a dozen turns and many tool rounds gave hundreds of readings, all in the heading, which a closed details element shows. The trace as a whole, verdicts and journal included, sat in the diff view's preparation area. (2) The walk window's profile choice writes the computer's default profile (`dspatch.review.presentationProfile.default`) as well as the walk's own choice; the diff view reads that default as the profile for the next preparation (`useDefaultProfile`) and compared it with `record.generation.profile`, so changing the reading profile made the diff view say the walks were prepared with earlier settings. The walk window's own panel (`ReviewView.tsx`, Step) had the same comparison against the reading profile directly, found by the window trial; both now say it for a difference of instruction version alone. The profile switch itself does what DSP-184 decided: a saved explanation is shown, or the missing one for the current step is asked for; nothing of the walk's structure is touched.

**Governing decisions.** docs/VISION.md section 3.4 (a walk is never an approval; reviews are instances; step explanations belong to Step; the DSP-189 entry: the trace readable on request and never in the reading flow) and section 13 (waiting shown as waiting; nothing missing shown as a positive result); docs/INTERACTION_MODEL.md section 1 and 4.5 (looking is not doing: closing a view stops nothing, cancel preserves what was done); docs/AGENT_BEHAVIOUR_AND_ORCHESTRATION.md section 1 and 5 (the drawing and the journal are the one account of a run; an agent's acceptance approves nothing); the run view rules already decided for the graph editor (DSP-28 #3 to #5, DSP-80, DSP-86: marking is a reading of the run's own journal, motion carries emphasis never meaning, a window that looks starts and stops nothing); docs/CODE_WALK_UNDERSTANDING_AND_PROFILES.md sections 9 and 10 (profile history and provenance per step).

**What is built.** (1) The diff view keeps only a short line in the preparation area, *Prepared through the planner, writer and reviewer loop* with a way into the run view, and a *Follow preparation* control on the running job line; verdicts, journal, usage, prompts and answers leave it. (2) The *prepared with earlier settings* notice is said only when DSpatch's instruction version differs from the one the walks were prepared with; the generation's profile, instruction version, provider, model and method stay as provenance, shown in the run view and in the walk's own text label, and the reading profile is the person's per walk. (3) A run view of its own, *Follow preparation*, in a window over the review: the loop's drawing drawn by the graph editor's own canvas, node shapes, run states and animations in a view mode (no palette, no inspector, no saving; zoom, panning and node selection), the run's actual path and ending, an activity panel beside it with every turn addressed to run, role, node visit and turn, following the active node by default and letting the person read an earlier visit while the run goes on, a compact summary (time, turns, reported usage with unknown as unknown, details on request), and Stop through the existing cancel. Opening and reopening starts no call; closing stops nothing. (4) The activity is what the provider and DSpatch actually report: streamed reply text, reasoning text where the provider exposes it (labelled as exposed reasoning, never as the model's whole thinking), tool calls with their subject and result where reported, commands with their output where reported, usage readings, DSpatch's own status (which step is being written, the mechanical checks, the outcome declared), the reviewer's verdicts and findings, and the turn's end. Kept with the run in `activity.jsonl` beside the record, so a finished run can be inspected; runs recorded before it show what they have (journal, verdicts, prompts and answers) with that limitation stated. (5) Usage readings are summed only per provider source across distinct observations (Copilot per API call, Claude and Cursor per turn, field by field, derived totals not added), unknown readings counted as unknown, nothing shown as zero for silence. (6) Reply and reasoning fragments are coalesced before they leave the host, events carry sequence numbers, a window opened or reopened during the run gets the state so far once and applies only later events, and the record is never resent whole per update.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Shared: `WalkLoopActivity` (addressed by run, node visit and turn, with sequence numbers), the run event payload for a review, the usage summary that sums only additive sources, the follow window's start.
2. Host: `runWalkLoop` announces the run, forwards the engine's journal and emits turn, note and verdict activity; `ReviewAgentJobs` turns the adapter's events of the active turn into activity (coalesced text), keeps the live run view and activity per job, writes `activity.jsonl` and `graph.json` with the record, emits run events to the review's windows, and answers `walkLoopRunView` from the live state or from disk.
3. Main and preload: the run event channel, the `walkLoopRunView` call, a follow window over the review opened from the diff window.
4. Renderer: `GraphCanvas` extracted from the loop editor (edge and node shapes, markers, bounds) with a view mode; `WalkLoopFollow` (graph, activity panel, summary, Stop, live following); the diff view's preparation line and the staleness rule.
5. Simulated provider: usage readings and reasoning deltas for the trial; tests for the fold, the summary, the stream and the job service; the follow trial in real windows, in CI; docs, release 0.1.15.
