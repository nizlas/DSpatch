Reached from the success branch of the previous step, `settle` is where the `Link` lets go of the callback that `startSession` registered (step W1.2) and arranges for it to be called, but not here and now. It takes the callback out of the `onSettled` slot, leaves the slot empty, and hands the call to a zero-delay `setTimeout`; `connect` gets nothing back from it and goes straight on to its `return`. Two consequences decide what the rest of the walk sees:

- **At most one report per registration.** The slot is emptied before anything is scheduled, so the callback cannot be called twice for one `whenSettled` call. A later `connect` on the same `Link` settles into an empty slot and schedules nothing, unless `whenSettled` has been called again first. For the same reason, a `Link` that was never given a callback settles silently: no error, no default report.
- **Nothing is reported inside `connect`.** The callback runs in a later turn of the event loop, after `connect` has already returned `'connected'` (the return of the previous step). When the walk goes back to `startSession` in the next step, the only report on this path is still pending in that timer.

<!-- dspatch:details -->

The order of the three statements is what gives those guarantees. The callback is first copied into a local, then the slot is set to `null`, and only then is the timer created with a closure over that local. So a `whenSettled` call that arrives after `settle` but before the timer fires cannot change what the pending timer will call; it only fills the slot for a future `settle`. The outcome is likewise fixed at scheduling time, as the literal `'connected'` passed from the success branch.

`setTimeout(..., 0)` means "no earlier than the next turn", not "immediately". By the runtime's rules, promise continuations already queued run before any timer, which is why `startSession` can resume from its `await` before this callback runs (the next step) and the callback is only seen running in step W1.7. How much later it actually runs depends on the host and on what else is queued; the code fixes only the order. One consequence worth weighing when judging the change: an exception thrown inside the callback does not propagate to `connect` or `startSession`, since a timer callback has no caller on the stack; it surfaces as an uncaught error in the host rather than as a rejected promise.

`settle` is `private`, which TypeScript enforces at compile time only; in the two source files of this revision its only callers are the two inside `connect`: the success branch followed here and the gave-up path after the retry loop, which this walk does not follow. Both go through the same detachment and deferral, so a gave-up report is equally delayed and equally single-use.

Against the earlier revision this method has no counterpart: `Link` there held no callback and `connect` returned `transport.open`'s boolean straight to its caller, so both the single-use slot and the deferred report are new with this change.
