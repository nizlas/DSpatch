`settle` is the Link's only hand-over to the registered callback, and it does two things in a fixed order: it takes the callback out of `onSettled` and leaves the slot empty, and only then hands the callback to `setTimeout(..., 0)` instead of calling it. Both halves decide what the caller can rely on.

Emptying the slot first makes the callback **one-shot per registration**: a `Link` reports at most once for each `whenSettled` call. A second `connect` on the same `Link` without a new `whenSettled` finds the slot empty, and `settle` then does nothing at all, no callback and no error, so that attempt ends with neither 'session ready' nor 'offline mode'. `startSession` registers on every call (step W1.1), so this path is covered; any other caller of `connect` has to do the same or hears nothing.

The zero-delay timer means the callback runs in a later turn of the event loop, after `connect` has returned and after whoever awaited `connect` has resumed, because promise continuations run before timers. So when `connect` returns `'connected'` on the line after the call here, **nothing has been reported yet**; the only report on this path is pending in the timer. The next step follows the return into `startSession`; the timer firing is step W1.7. The gave-up end of the loop calls `settle` the same way, which the second walk follows.

The local `callback` is taken before the slot is cleared, so the scheduled closure holds its own reference. A `whenSettled` call made after this point, including one made from inside the callback when it finally runs, lands in an already empty slot and stays there for the next `connect`; nothing here can overwrite or lose it.

Running from the timer also isolates the callback from `connect`: an exception thrown inside it cannot reject `connect`'s promise or `startSession`'s, it surfaces as an uncaught error in the timer, and `settle` neither awaits nor inspects what the callback does. Zero delay is a minimum, not a position in the queue; a timer or I/O event already queued runs before it. On this walk's path no other timer of the Link is pending, since `pause` is awaited only after a failed open and has elapsed before the next attempt.

Within these two files only `connect` calls `settle`, from its two outcome sites, and only `whenSettled` and `settle` write `onSettled`; `private` is a compile-time check in TypeScript, so this is what the files show, not a runtime guarantee. In the From revision none of this exists: `connect` returned the transport's boolean and the caller learned the outcome only by awaiting it, so this method is what turns the callback into a second, later channel beside the return value.
