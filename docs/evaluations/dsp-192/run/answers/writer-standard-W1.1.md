`startSession` is where a session's connection is started: it is given a `Link` and an address and asks the `Link` to connect. In the earlier revision that was all it did (src/session.ts, base lines 3–5): a bare `await link.connect(address)` whose boolean answer was dropped, and a `Promise<void>` that resolved identically for a true and a false answer from the transport, so the caller could not tell the two apart. Here it takes a third argument, `report`, a function that accepts a line of text, while its return type is still `Promise<void>`: whatever the caller learns about the outcome will arrive through `report`.

The first thing `startSession` now does, before any connection is attempted, is hand the `Link` a callback through `link.whenSettled`. The callback is an arrow function that closes over `report`, that is, it keeps using the `report` this call received: when the `Link` calls it with an `Outcome`, it reports `'session ready'` for `'connected'` and `'offline mode'` otherwise. `Outcome` is the `Link`'s own two-value type, `'connected' | 'gave-up'`, so "otherwise" is exactly the gave-up case, and the translation from the `Link`'s vocabulary into the words a person sees is made here in `startSession`, not inside the `Link`.

**Registering calls nothing yet.** `whenSettled` only stores the function, and `report` has not been called when this line completes. What the reader takes onward: the `Link` now holds this callback, and `connect` is called right after it, on the next line, with the callback already in place. When, and whether, the callback runs is decided inside the `Link`, which the next steps trace.

Why the registration comes first. `whenSettled` is a plain store into a field (src/link.ts, target lines 13–15, the next step), and the `Link` reads that field back when an attempt settles, later inside `connect`. Had the callback been registered after the `await`, the `Link` would have looked before anything was there, and the outcome would never have reached `report`. Nothing can run between the registration and the start of `connect`: both are synchronous statements of the same function, and `connect` runs up to its first `await` before `startSession` yields.

What the closure carries. `report` is the parameter of this particular call, and the arrow function keeps it reachable for as long as the `Link` holds the function. Nothing here ties the callback to `startSession`'s own lifetime; the last step of this walk shows that it can run after `startSession` has returned. So the `report` a caller passes must be one it is prepared to have called later, not only during the `await`.

What cannot be established here. These two files contain no caller of `startSession`, so what `report` does with the text, whether it logs it, shows it or records it in a test, is not visible in this code. Its type promises only that it takes a `string` and that nothing is expected back; `whenSettled` likewise accepts a function returning `void`, so the callback's result is dropped.

`'session ready'` is produced nowhere but in this callback. The only other `report` call in `startSession` is a direct `'retrying later'`, under a check that a later step (W1.6) shows is skipped on this walk's path.
