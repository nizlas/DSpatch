# DSP-192 · The three profiles on one locked walk · judgment

Nine texts for the same walk plan, the same revision pair and the same two steps, each answered by the same stand-in model with the same read-only access to the code. This file is the judgment of those texts: whether they are true to the code, and whether each gives the reader its profile names the help the reference (docs/CODE_WALK_UNDERSTANDING_AND_PROFILES.md, version 1.1) asks for. No word counts were taken; length is read off the texts only where it is a consequence worth naming.

**Not evidence of a provider.** Every prompt was answered by a Claude model running as a Claude Code subagent outside DSpatch's providers, reading the revision folder with Read, Grep and Glob. The DSP-189 Standard texts used as the comparison point were made the same way (a file-backed stand-in through the product path). Whether Niclas's provider behaves as these texts do is not established here.

## Correctness against the code

Every claim in the nine texts was checked against the two files at both revisions. No text states something false about the code. Three claims rest on more than the code shows, and one rests on the plan rather than the code:

- `writer-pedagog-W1.5`: "TypeScript requires the explicit `!== null` test before the call is allowed". True only with `strictNullChecks`; the revision holds no compiler configuration. A reviewer applying the reference's "a statement about the code that is not true" would ask for "with strict null checks" here.
- `writer-standard-W1.5`: "hosts may round it up to a millisecond or a few when timers nest". General runtime knowledge, allowed by the reading rule on what follows from the language's or library's rules, and the text itself says nothing depends on the figure.
- `writer-essens-W1.1`: "`report` … is called synchronously and its result is ignored". The call is synchronous within the timer's turn; the sentence can be read as if the call happened during `startSession`, which the same text's next sentence rules out.
- `writer-essens-W1.5`, `writer-essens-W1.5-v7`, `writer-standard-W1.5`: "the second walk" follows the gave-up exit. The plan given to the writer has no second walk; the phrase comes from W1.4's brief. In the product the whole plan is given, so this is a limit of the harness, not of the texts.

The two Path B answers end with the references block the channel asks for and include step references (`{"label": …, "step": "W1.1"}`) beside the path references. The channel's answer format documents only path references; the product's parser (`stepReferencesFrom` in `review-discussion.ts`) accepts both, so these answers would render with working links.

## W1.1, the simple step

**Essentials (v8).** Opens: "`startSession` has a new third parameter, `report`, a sink that takes one line of text for the user; the earlier revision took only the `Link` and the address and did nothing but await `connect`." The first part selects three things: why the code is here (a report sink), the main work (a callback registered before `connect`), and the decisive consequence ("**Registering runs nothing.** … `'session ready'` can only ever reach the user through this callback"). It leaves out the closure concept, the `Outcome` type, `async` and `Promise<void>`. After the marker it continues with what an experienced developer would want next: the double report on the gave-up path, and that a second `startSession` on the same `Link` replaces the first registration. This is an accurate main picture at a higher level; what it leaves out is exactly what Standard explains, so it is not Standard compressed.

**Standard (v8).** Opens: "`startSession` is where a session's connection is started: it is given a `Link` and an address and asks the `Link` to connect." It makes the mechanism understandable: the closure ("it keeps using the `report` this call received"), the two-value `Outcome`, "**Registering calls nothing yet.**", and after the marker why the registration comes first, what the closure carries, and what cannot be established from two files without a caller. Against DSP-189's Standard W1.1 (`../../dsp-189/connect-loop-standard-2.md`, which opens "`startSession` now takes three arguments instead of two" and bolds "Registering the callback runs nothing."), the content, the level and the deepening topics are the same. Standard is preserved: its reader text did not change between version 7 and 8, and its output here is of the same kind as before. One weakness: the text names "src/session.ts, base lines 3–5" and "src/link.ts, target lines 13–15" in the prose, against the walk rule that asks for functions and types there. That came from a contradiction in the writer's prompt, fixed after this run (see below).

**Teacher (v8).** Builds the understanding the reasoning presupposes before using it: the type read aloud ("a function that takes one string and gives nothing back"), the difference between handing over a function and calling it ("Giving someone your phone number is not a phone call"), and the closure, named and explained ("A function in TypeScript (as in JavaScript) keeps access to the variables of the place where it was written, even when it is run later from somewhere else; this is called a closure"). Its facts are Standard's facts; what it adds are concepts, not more facts, and its deepening is the next layer (the compile-time-only guarantee of `Outcome`). It is the longest of the three as a consequence of that building. For a step this simple no profile answered in "a few words"; the brief asks the writer for four things, so W1.1 is not the trivial kind of step the reference means.

## W1.5, two mechanisms

**Essentials (v8).** Opens: "`settle` is the Link's only hand-over to the registered callback, and it does two things in a fixed order … Both halves decide what the caller can rely on." The first part selects the two guarantees ("**one-shot per registration**", the later turn) and the consequence the walk carries onward ("**nothing has been reported yet**"), and notes that `startSession` registers on every call so this path is covered. The mechanics go after the marker: that the timer's closure holds its own reference, that an exception in the callback cannot reject `connect`'s promise, and that zero delay is a minimum, scoped to this path ("no other timer of the Link is pending, since `pause` is awaited only after a failed open"). Chosen, not compressed.

**Essentials (v7, same prompt otherwise).** Opens: "Reached from the success branch of the previous step, `settle` is where the `Link` lets go of the callback that `startSession` registered (step W1.2) and arranges for it to be called, but not here and now." Then two bullets: "**At most one report per registration.**" and "**Nothing is reported inside `connect`.**" Its deepening retells the order of the three statements ("The callback is first copied into a local, then the slot is set to `null`, and only then is the timer created"), the timer's rule, the exception, `private`, and the earlier revision.

With this stand-in, the v7 and the v8 Essentials come out at a comparable level: both are a selected main picture, and the v7 text is the shorter of the two. The difference is in the deepening, where v8 continues with what the experienced developer may want next and v7 goes through the statements in order, and it is small. The behaviour that motivated this task, Essentials coming out as a compressed Standard, was observed with Niclas's provider and is not reproduced by this stand-in under v7. So this comparison shows that the version 8 wording does not make Essentials worse and that its deepening takes the intended shape; it does not show that version 8 cures what version 7 did with the real provider. That check is open.

**Standard (v8).** Opens: "Here the Link uses the callback that `whenSettled` stored in `onSettled` (step W1.2), and the way it uses it decides how the new report channel behaves: the callback is detached first and then deferred, not called." The mechanism follows: the local copy and why it makes the order work, "**One registration therefore yields at most one report.**", the zero delay as a later turn, and what to take onward. It keeps the code apart from an interpretation: "The code shows the deferral but not its reason. One reading is that the caller is then sure to see `connect`'s return before any report … that is an interpretation, and the code states no such intent." Against DSP-189's Standard W1.5 (which opens "`settle` is reached from the success branch with `'connected'` as its `outcome`, and it does two things in a deliberate order" and bolds "the slot is already empty when the callback is arranged"), the two things come in the same order, and the deepening covers the same ground (the closure over the local, the discarded timer handle, the exception in the timer, `private` as a compile-time check); the v8 text adds a list of special cases. Standard preserved.

**Teacher (v8, writer path).** Opens with a numbered retelling of the three statements ("It copies … It empties … If the copy was not `null`, it hands `setTimeout` …") and then builds what the reasoning needs: "JavaScript runs each piece of synchronous code to completion on a single thread, so no other code can read or write the slot between the copy and the clearing", the event loop as a queue, and a counterfactual that makes the deferral's effect visible ("Had the method written `callback(outcome)` directly, `report('session ready')` would have run inside `connect`, before the caller even saw the return value"). The deepening is the next layer: microtasks before tasks, the cases that change the outcome, the union type and `private`. The opening list is the one place in the set where a Teacher text inventories lines, which the instruction discourages; the Path B Teacher below shows the same step without it.

**Essentials (Path B, made after the walk from the Standard text).** Opens: "`settle` is where `connect` tells the listener registered through `whenSettled` how the attempt ended; both of `connect`'s exits go through it". It selects "Two choices in `settle` decide what the reader must expect from that path" and ends the first part with "The consequence to judge: the return value and the callback are two channels for the same outcome, and the return value arrives first." It did not keep the Standard text's order or sentences; it chose again. Equal in level to the writer-path Essentials.

**Teacher (Path B).** Opens: "`settle` is where the registration made in `startSession` (W1.1) is consumed. It does not deliver the report: it takes the callback out of `Link`'s one slot and asks the host to run it in a later turn. Two guarantees follow, and the rest of the walk rests on both." It builds the two concepts the step needs and nothing else: single-use through one thread and run-to-completion, with an insight the other texts lack ("Note that the order of the two lines, clear then queue, is not what prevents a double call; the clearing before `settle` returns is."), and deferral through the host's task queue, with an image ("posting a note rather than tapping someone on the shoulder"). It recalls W1.1, W1.2 and W1.4 in a line each. The deepening is the next layer: what the host allows between queueing and firing, both branches, re-registration, exceptions, and why the two channels exist is "not something these two files explain". The best Teacher text of the set.

## What the comparison shows, and what it cannot

- All nine texts are true to the code, with the four notes above.
- The profiles differ in selection and level, not in facts. Essentials leaves the closure and type mechanics to the code, Teacher adds concepts and not facts, Standard explains the mechanism; the same two guarantees of `settle` and the same order in `startSession` appear in all of them. Length falls out of that: Teacher longest and Essentials shortest in both steps, with no count asked for.
- Path B (an alternative made after the walk from the Standard text) is comparable with Path A (written during the walk), and the Path B Teacher was the better Teacher text. One sample per cell: no conclusion about the paths follows.
- Version 7 against 8 for Essentials: a small difference with this stand-in, in the deepening's shape. The real-provider check remains open.
- Not run: the reviewer's turn. The reviewer's new rule (judge the help for the profile's reader, not the amount of material) is untested in output.

## Clear faults fixed once

- The writer's prompt told it two incompatible things: the walk rules ask for functions, types and values in the prose, and the folder section's closing sentence asked it to name places by path, side and lines. Standard W1.1 followed the second. The writer's prompt now ends the folder section with its own sentence: the places beside the text already name files and lines; name a place by path and lines only when pointing at code outside this step's places (`walk-loop.ts`, `WRITER_PLACE_NAMING`). This came after the run; the saved answers were made before it and were not regenerated, since the fix concerns naming, not the profile's help.
- No fault in the profile instructions themselves called for a change, and no prompt was tuned and rerun.

## Remaining weaknesses

- The stand-in is not a provider, and one sample per cell is not a distribution; the open question is whether Niclas's provider under version 8 gives Essentials and Teacher this shape.
- The writer has no checked reference of its own: when it points at code outside the step's places (the gave-up exit at line 28, `pause`), it can only name path and lines in prose. A design gap of the DSP-189 loop, left as it is.
- Essentials for a simple step is still several paragraphs when the brief asks for several things; the reference's "a few words" holds for steps whose brief asks for one.
- One Teacher text opened by inventorying the statements; the instruction discourages it but does not prevent it.
