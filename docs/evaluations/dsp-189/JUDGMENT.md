# What the loop adds: the comparison across five synthetic cases (DSP-189, 10 November 2026)

Written for the task report from the materials in this folder. The texts were produced on DSpatch's real product path with a file-backed stand-in for the provider, answered by Claude subagents outside DSpatch's providers (see README.md). **Nothing here is evidence of the product path with Niclas's provider on real code**; that judgment is his and the task's acceptance criterion 5 stays open for it. Two independent judges (one per case, with no sight of each other or of this text) wrote JUDGMENT-connect.md and JUDGMENT-work-queue.md against the code; the other three cases were judged by the task's author from the materials and the reviewer's own checked assessments.

## What the loop did on these cases

**The planner.** Every plan followed the program rather than the files: an entry point, the calls, a return, alternative outcomes as separate walks that start again at the branch ("Back at the branch: open is false"), the hand-over to a worker or a timer callback as its own step with the execution context named, a departure from execution order announced ("A pause in the execution order to look at the state the next steps use"). Each step carried a brief for the writer that named what the step must make comprehensible and how it is reached. The one call produced comparable structures in every case and, twice, a structurally better choice in the first round: a visible walk for the rejecting transport (connect W3) where the loop had put the rejection into a Show more deepening (the second loop run planned that walk), and a walk over the removed code (work-queue W4).

**The writer.** One step per call, with the plan in view, gave texts that hold the reader at every transition, name the execution context of a callback ("in the timer's context: on an empty call stack, with no `startSession` frame above it"), carry consequences a reviewer needs (no timeout in `connect`; the join deadlock the destructor's block avoids; the job never counted when the queue dies before its worker first locks) and have a deepening behind every step. The one call's texts were correct and at the same Standard level on the central places (`acquire`, the worker's wait, the slot's `get`), but told where the loop walked (the callback never got a step), and had deepenings on only a few steps. The loop's cost is length and repetition: hypotheticals in first parts where Show more would serve, and the same argument derived again in several steps (the lock discipline up to eight times in work-queue) although the writer's instruction says to recall it in a line and its session knows the earlier steps.

**The reviewer, first instruction.** It accepted at once in four cases out of five, each time with a detailed assessment that shows it read the code (quoted lines, checked orderings and worked examples), each time noting one or two small imprecisions it did not treat as findings. Both independent judges agree the acceptances were defensible and that no text contains an error that misleads about the change, but both found that the sentences the reviewer called "loose" were wrong (one-clause fixes), that it missed one over-generalisation (connect W1.1) and two internal inconsistencies (work-queue W1.5, W1.7), and that it did not flag the re-derivation. In that round the reviewer added confidence, not correction. In the fifth case (external context) it requested a correction round for a structural gap that turned out to be a defect in DSpatch's own prompts (below), so the round, the replanning and the final assessment with a remaining objection were exercised on real text, and the loop found a product fault that no simulated trial had.

**The reviewer, sharpened instruction.** After the instruction was changed so that a statement about the code that is not true is a finding whatever its size, both re-runs had a correction round of the kind the loop is for. In connect it found two false statements (a Show more that gave the overlapping-registration consequence to the wrong channel; an incomplete inventory of where the `Outcome` type is used), the writer rewrote exactly those two steps in its session, and the final assessment verified the corrections against the code and accepted. In context it found three (a comment line the text said was not there; a muddled paragraph about `Math.trunc` against the caller's threshold that claimed a band where the two decisions disagree, when none exists; a rule about the regular expression in exponent form that is false in general), all true, all corrected in the three rewritten steps, and the final assessment accepted. The first drafts and the final texts stand side by side in `context-loop-standard-2.md` and `connect-loop-standard-2.md`. Whether this threshold also produces needless rework on other code is not established; on these runs every finding was a real error.

**The one call against the loop, in one line per case.** connect: loop better on orientation, callback context and depth; one call shorter, shows base beside target, better structure on rejection in the first round. work-queue: loop better on the hand-over, the return to the caller and the destructor; one call half the reading, the predicate form the reader needs, one omission at the destructor. setting: both correct and complete for a three-place change; the loop's five steps against the one call's eight over two walks; the loop deeper on `Number()` and the guard, the one call lighter. snapshot: both explain the pointer-under-lock mechanism at Standard level with exact guarantees; the loop adds the never-null invariant and the fate of the previous snapshot as steps; the one call a destruction-inside-the-critical-section observation. context: the loop's texts explain the library at its declared version and what the evidence does not cover; the one call does the same in four steps.

**Explain this** on the same lines (unchanged prompt and answers from DSP-188) remains the best ordered trace of what the lines do; both walk sets reach its level on the central place, and the loop's step adds the judgment a reviewer needs (what decides the outcome, what is only requested, what is not covered).

## What the evaluation found about the product

- **A defect in the loop's prompts, found by the loop.** The planner's context places (another repository of the workspace, DSP-175) were kept in the delivered definition but not shown to the writer and the reviewer, and a changed context place did not count as a changed step. The reviewer's structural finding in the first context run was about exactly that; the planner replanned with the same places, nothing was rewritten, and the objection stayed. Fixed in this task (reviewed and context places rendered together in every role's prompt; the step signature includes context places; a test covers it), and the case was run again after the fix.
- **The reviewer's threshold.** With the first instruction a false sentence that did not change the picture was not a finding; with the sharpened one it is, and the correction round then worked as intended on two cases. The risk the other way, rework on trivia, did not show in these runs.
- **Repetition across steps.** The writer's session knows the earlier steps and its instruction says to recall rather than derive again, but the first part of each step is still written to stand alone. Not changed in this round beyond the sentences above; a reviewer that treats it as a finding, or a writer instruction that names it harder, are the candidates.
- **Wait and usage.** With the stand-in the loop took three to four times the one call's wall time, most of it the planner's single call and the writer's one call per step; the reviewer's calls took half a minute to five minutes. Real provider latency and usage are unknown.

## Limits

One model as stand-in for all roles and for the one call; synthetic cases without tests or callers; no run with Niclas's provider. The one call's texts were produced by the same stand-in on the same day, so the comparison is between paths, not between models. The judges and the stand-ins are the same model family; their agreement is not independent evidence of correctness, and the code was read, not run.
