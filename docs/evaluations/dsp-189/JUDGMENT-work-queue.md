# Judgment: work-queue, Standard — loop versus one call versus Explain this

Judged against both revisions of the three files (base `0979a4c`, target `5bf9107`) and CODE_WALK_UNDERSTANDING_AND_PROFILES.md sections 1–5 and 11. "Loop" is `work-queue-loop-standard.md`, "single" is `work-queue-single-standard.md`; step ids are the delivered ones.

## 1. Correctness

No set states a wrong fact about the central mechanisms. All three say correctly that `lock_guard` holds `mutex_` for the whole of `acquire` including the `notify_all`; that `operator[]` inserts a null `shared_ptr` before `if (!slot)`; that `notify_all` wakes only threads waiting at that instant and is otherwise dropped; that the worker holds the mutex at every moment it is not inside `wait`, so the only lost-notify window is before its first `lock(mutex_)`; that the stop cannot be missed because `stopping_` is written under the mutex and `wait` releases it atomically; and that the returned `shared_ptr` shares the object the worker writes to under a lock the caller cannot take. Explain this is correct throughout. What remains are imprecisions:

- **Loop W1.5, Show more:** "if the worker has by then re-entered `wait` the notification wakes it, and if it has not, the case of a later step applies (W1.8)". After a scan the worker releases `mutex_` only inside `wait`, so a submission blocked on the lock always finds a waiter. The hedge cannot occur and contradicts W1.7 and W1.8 Show more, which say so correctly.
- **Loop W1.7:** "a submission that finds the flag already raised still costs the worker a wake-up". In the coalescing ordering the worker is already notified and reacquiring the mutex; the second notify finds no waiter. One wake-up, not two.
- **Single W2.3:** "the destructor's `notify_all`, which triggers one more scan before the loop ends (next walk)". Only if the worker is waiting; if the destructor runs before the worker's first lock there is no scan and the job is never counted. Single W3.2 gives that ordering without this consequence; loop W2.5 states it: "no final scan happens, so a job marked pending in that interval is never counted".
- **Single W3.1, misleading by omission:** "Releasing the lock before `notify_all` is not needed for correctness; it lets the woken worker re-take the mutex without first waiting for the destructor to release it." True of the notify, but the same block releases the mutex before `join`, and that is essential: joining while holding `mutex_` would wait for a worker that needs `mutex_` to leave `wait`. A Standard reader may take the block for an optimisation. Loop W2.4 has it: "Joining while still holding the mutex would wait for a worker that is itself waiting for the mutex."

The reviewer noted two trivial slips and raised no finding. It did not notice the W1.5 hedge or the W1.7 sentence; neither misleads about the mechanism, so accepting was defensible, but they are exactly what a reader of the whole walk catches and a per-step writer cannot.

## 2. Following the course

**Loop.** W1 is a genuine course: caller → `acquire` lookup → the type as a declared detour → mark, notify, return → "A change of thread" into the scan (W1.5) → "Back on the caller's thread" (W1.6) → back at the branch for the existing slot (W1.7) → back at the hand-over for the not-yet-waiting worker (W1.8). Every transition section 1 asks for is spoken. W2 runs construction → member order → lock and wait → destructor → exit with both orderings apart. The reader is held throughout, and tired by repetition: the lock-discipline argument (the worker holds the mutex except inside `wait`, so `acquire` runs only while it waits) is derived in W1.4, W1.5, W1.7, W1.8 and W2.3 and in four of their Show more parts. Section 2's "recalled in a line … not derived again" is not honoured, because each writer call cannot know what the previous call proved. W1.5 also opens "until now that thread has been blocked inside `cv_.wait(lock)`", and only W1.8 says that is not guaranteed; single W1.4 gives the caveat at once: "The exception is the moment before the worker has taken the lock for the first time, treated in the next walk."

**Single.** Four tight walks. W1 stops at `return slot`; the hand-over is pointed at ("the run itself happens later, on the worker thread") but not walked, so the reader leaves W1, passes the class and constructor, and reaches the wake-up and scan in W2.3–W2.4. The thread switch is explicit: "From this point there are two execution contexts in play. The rest of this walk follows the **worker thread**" (W2.2). There is no return to the caller; the handle's data race is settled at the type (W1.3), and the existing-slot branch is folded into prose. W4 on the old code is a justified removed-behaviour item. The loop is closer to the reference's model of registration, then the worker; the single to its economy.

## 3. Explaining the shown place

**`acquire`.** Explain this gives the lock, `operator[]`, the reference into the map, one slot per key, the flag as the request, notify-under-lock ("the worker wakes but waits for `acquire` to return and release the lock before it sees the new state") and shared ownership, then coalescing, the start-up window and the private lock. Both walk sets reach that level: single W1.2 + W1.4 with the same precision plus the allocation-failure null entry; loop W1.2 + W1.4 + W1.7 plus node-based map stability, `notify_all` versus `notify_one`, and the return value constructed before the `lock_guard` dies. Nothing in either is merely named.

**The worker's wait.** Single W2.3 is the best single step in either set: `unique_lock` versus `lock_guard`, the atomic release-and-wait, the no-predicate consequences, and the standard predicate form in Show more. Loop W2.3 says the same without the fix form and adds `stopping_` as a plain bool under the lock, no deadline, and an escaping exception terminating the program; the lost notify is W1.8's own step.

**The destructor.** Loop W2.4 explains the block as deadlock prevention for `join`, the dropped notify being harmless because the flag is checked before every wait, and reverse destruction. Single W3.1 explains the order and the under-mutex reliability well but mis-sells the block. The loop wins this place.

## 4. The deepening

The loop has Show more on all 15 steps, the single on five of 13. The single's all add (allocation failure, coalescing order, non-movability, the predicate form, the mid-scan case); two steps needed one and have none: W2.4, the scan, for the spurious-wake cost and the null dereference, and W3.2 for the never-counted job. The loop's mostly continue but several restate first: W1.4's first part already says "a thread woken from `cv_.wait` must reacquire that mutex before `wait` returns", and its Show more opens "the worker's `wait` is woken by the notify but blocks inside `wait` on `mutex_`"; W2.2 and W2.3 Show more repeat their destruction-order and lock-timeline sentences before the new facts. The reviewer's "deepen the first part instead of repeating it" is true of what they add and generous about how they begin.

## 5. What the loop added, and what it cost

Added by the loop: the return to the caller and "the one point in this revision where `pending` and `runs` can be read without a concurrent writer" (W1.6); the existing-slot path with its two timing outcomes (W1.7); the lost notify as a step with its shutdown edge (W1.8, W2.5); the join deadlock (W2.4); "the new thread runs it on the very object that is still being constructed" (W2.1); that removing `find` removes a side-effect-free query (W3.2 Show more). In the single and not the loop: the predicate form a reader needs to judge the risk; the interface before and after as a shown pair (W4.3); and roughly half the reading. The reviewer caught no real shortcoming, asked for no rewrite, verified the weighty claims accurately, and missed the two inconsistencies and the re-derivation. Cost: 17 turns and 17 min 7 s against one turn and 5 min 13 s; usage unreported.

## 6. Net verdict

Both sets are correct where it matters and both reach Explain this's level on `acquire`; the choice is not about accuracy. The loop's course is the better one for this code: it walks the hand-over into the worker and back, treats the alternatives at their branch points, and explains two things the single leaves thin, the deadlock the destructor's block avoids and the job never counted when the queue dies before its worker first locks. It pays with a walk more than twice as long in which the same lock argument is proved up to eight times and some deepenings restate before they add, because each writer call starts without memory of the last and the reviewer did not treat that as a finding. The single reads faster, holds the reader with precise cross-walk pointers, and errs once by omission at the destructor. For a reader who wants a concurrent change's course followed properly, the loop's extra wait buys a real but modest gain; for one who will read `acquire` and the wait and judge the rest from the code, the one call already gives that. The reviewer round added confidence, not correction.
