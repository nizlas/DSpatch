**Where we are:** the script has checked the container ([W1.3]), made sure debugpy is installed ([W1.5]) and prepared the log folder ([W1.6]). This line is the last thing it does. Its job is to leave a debuggable `orders.main` running inside `orders-dev`, ready for VS Code to attach to in the next step ([W1.8]).

**What `docker exec -d` means.** `docker exec` runs a new process inside a container that is already running. Here that container is the `dev` service, which only runs `sleep infinity`, so the service itself is never started by Compose. Without `-d`, `docker exec` stays attached: it streams the process's output and returns only when the process ends. That is how the earlier `docker exec` calls in this script work, and why each of them finishes before the next line runs. With `-d` (detached), Docker starts the process and `docker exec` returns straight away. The exit code only tells you whether the process could be started. It says nothing about whether the program inside later succeeds. The process now belongs to the container, not to the script. It keeps running after the script exits, and its output is not shown anywhere the script or VS Code can see.

**What the started process does.** `python -m debugpy … -m orders.main` is like running `python -m orders.main` with a debug server wrapped around it:

- `--listen "0.0.0.0:$PORT"` opens a TCP port that a debugger can connect to. The address `0.0.0.0` (all interfaces) matters here. The published port `5678:5678` in `compose.yaml` ([W1.4]) forwards host traffic to the container's network interface. A server bound only to the container's `127.0.0.1` would not receive it.
- `--wait-for-client` makes debugpy hold back before running any of `orders.main`. Nothing from `main()` runs until a debugger connects: the log setup and `serve(port=8000)` ([W1.9]) both wait. This is what lets you hit breakpoints in startup code. It also means the service is not usable at all until someone attaches.
- `-m orders.main` works because `docker exec` uses the container's working directory by default. That is `/workspace` from `compose.yaml`, where the repository is mounted, so the `orders` package can be imported.

**Why detached is needed.** With `--wait-for-client`, an attached `docker exec` would block forever. debugpy waits for VS Code, but VS Code only attaches after the pre-launch task finishes, which would be a deadlock. In `tasks.json` the task is a plain `shell` task with no `isBackground` setting, so VS Code treats it as done only when the script exits. `-d` lets the script exit with success while debugpy keeps waiting in the container.

**What this does not guarantee.** When the script exits, debugpy has been *started*. It is not necessarily *listening* yet: Python still has to start up and import debugpy before the port is open. Nothing in the script waits for the port, so VS Code's connection to `localhost:5678` in the next step can arrive before the server is ready. Whether that causes a failed attach depends on timing and on how the VS Code debugpy extension handles a refused connection. Neither can be seen in this repository.

**Failures that `-d` hides.** Since the process's output goes nowhere visible, problems after the start leave no trace in the task output. The task still reports success. Two cases the code allows:

- **A port already in use.** A previous session's debugpy may still be running in the container, for example if the service is still serving or still waiting for a client. The new debugpy then cannot bind `0.0.0.0:5678` and exits. The attach in [W1.8] may still succeed, but it connects to the *old* process, which may be running older code. Nothing in the script checks for or stops an earlier instance.
- **An import error in `orders.main`.** This only shows up after a client has attached, because `--wait-for-client` defers running the module. You would see it in the debug session, not in the task.

**Three settings that must match.** The port appears in three places that are not linked to each other: `DEBUG_PORT` in `tasks.json` (also the default in the script), the published `"5678:5678"` in `compose.yaml`, and `connect.port` in `launch.json`. If you change one without the others, the attach goes to a port nothing listens on, or to a port the host never forwards.

**Which user the service runs as.** This `docker exec` passes no `--user`, so `orders.main` runs as the container's default user. In the `python:3.12-slim` image that is root, which is why [W1.6] hands `/workspace/logs` to the host user beforehand. When `main()` later calls `LOG_DIR.mkdir(exist_ok=True)`, the folder already exists. Note that the log *file* it creates will itself be owned by root, a detail [W1.9] takes up.

**Compared with the base revision.** In the base revision there is no script. `launch.json` uses `"request": "launch"` with `"module": "orders.main"`, so VS Code started the module locally and owned the process. Here VS Code owns nothing: this line starts the process, and VS Code only connects to it.
