# Generic agent network

Run the graph from live chat for a conversational workflow. Opening the graph in the editor is for inspection and editing; the editor's live Run binding does not run this template. `stored-result` carries reply bodies for handoffs during the run; supplying a results directory alone does not write those bodies as files. Do not assume durable reports or resumability from this graph: verify the recording and recovery behavior of the chosen run path, and save any needed report through an authorized project mechanism.

This template has write-capable steps. DSpatch may read the working folders for snapshots even when the agent is instructed not to read them; the instructions neither disable host observation nor enforce permissions. Do not use this template when the mandate prohibits all project access or observation. Whether observation is allowed, and which runtime or provider controls apply, must be established for the actual environment.

Every role returns a carry-forward ledger of accepted slices with attributed evidence. Each edge supplies only the named results, and each step must carry the ledger in its actual reply, including failures. Agent instructions are not a guarantee of model compliance; inspect results and reconcile missing or uncertain evidence.

The call limit is checked after each step. If a limit is routed, later reporting calls may exceed it. If the limit is first spent at a reporting node, those nodes have no limit route and the run stops without reaching the report-delivered ending; it may stop before the final report step runs. Without limit routing, the run stops at the limit. A report-delivered ending is not human approval or proof of verification.
## Choosing and running it

The graph ships with DSpatch and is listed as **Generic agent network** in the graph editor's **Graph** list, beside the other bundled graphs, in every project. Opening or choosing it starts nothing, and it is never preselected: a workspace keeps the loop it last chose. Run it from the project chat with **Use workflow**. The agent and base model are those chosen in the chat; every step inherits them. Requirements are checked against that agent's actual integration.

Project instructions come from the open project, through the context DSpatch gives every graph run started from the chat: the first step is told which instruction files are present in the working folder (names only, such as `AGENTS.md`), and every step works in that folder and reads what its task needs. Later steps receive the person's words rather than the whole snapshot, so they find the instruction files in the working folder themselves. The template adds no instructions of its own beyond the roles and node tasks shown in the editor.

## One node per role, with a model class and a review route per slice

The Implementer, Researcher, Explorer, Reviewer and Skeptic are one node each (DSP-224; the small/medium/large variants of DSP-222 and earlier are merged). With each capability, Tech Lead's dispatch states two choices on their own `CHOICE:` lines, each with a short reason, independently of each other and of the capability it names:

- **`class`** — the model class the work needs: `small`, `medium` or `large`. The Implementer offers all three, the Researcher medium and large, the Explorer small and medium; a class a step does not offer runs its default, and the run records why.
- **`review`** — the checks the work goes through: `standard` (QA, a bounded review and a bounded challenge, either of which may escalate to the thorough check) or `thorough` (design QA, a design and correctness review and a full challenge). For the Implementer it decides whether QA or design QA follows; for the Researcher, the challenge. Explorer and Data Curator work is always checked on the standard route and Infrastructure and Experiment Analyst work on the thorough one, as before the merge: their edges set it.

The Reviewer and the Skeptic take their model class from the route (standard: small, thorough: large). An escalation — the review's `design-review`, the challenge's `escalate` — returns to the same node with the route set to thorough; a thorough visit is not offered the escalation again. The choices travel with the slice through revisits and rework until the next dispatch decides again, so one slice's choice never reaches the next slice's work; a dispatch that states none takes the defaults (medium, standard). Each visit's record carries the choices, who decided them and why, and the model and class it ran with.

The class is mapped to a model per agent in the graph editor's **Model classes…** setting (saved under `modelClasses` in `dspatch-model-choice.json`), never in this graph. While a run walks, a node whose class is chosen per visit shows the class its latest visit runs with on a tag (*Small*, *Medium*, *Large*, or *S*, *M*, *L* when zoomed out), with the visit number and model on the line below; the tag's hover adds how it was decided, and, for a class set to *Use chat model*, which chat model it resolved to. Before a run the node says the class is chosen per visit.

Still separate, because their tasks differ: the planning gates (`reviewer-readiness`, `reviewer-plan-gate`) and the job plan review (`reviewer-job-gate`) use the Reviewer role on steps of their own; QA and design QA are different checks on the two routes; and the Tech Lead's steps (planning, selection, dispatch, escalation, acceptance, report) keep their two roles, Tech Lead and Tech Lead (medium), whose instructions differ in scope rather than in size alone.

## Parallel branches, when the work splits

Tech Lead's dispatch has one more choice besides the capabilities: **`parallel`** (DSP-226). It is for a subtask that splits into two to six parts that can be done at the same time without writing the same files and without one part needing another's result. Everything else is dispatched to one capability as before, which stays the usual way; nothing in the graph sends ordinary work through the branches.

With `parallel`, the dispatch writes one `dspatch-slices` block. DSpatch writes the block's format, the capabilities a branch may run as, the choices a branch may set and the rules into the dispatch's prompt from the `branches` node's settings (DSP-227; [GRAPH_FORMAT.md, *Fan-out*](../GRAPH_FORMAT.md)); the dispatch's purpose keeps only this graph's criteria, such as which capability runs which class. Per branch it states the task and expected result, the capability it runs as (`as`: the Implementer, Researcher, Explorer or Data Curator; the Implementer when absent), its own `choices` (model class and review route), the paths only it may change, the shared contracts and settled dependencies it works against, its acceptance criteria and its check. DSpatch reads and validates the block before anything starts. It refuses the split, and no branch starts, when two branches would write the same path, when a branch depends on another branch of the same split (`dependsOn`: such work is dispatched in a later round after integration, or in sequence), or when a branch names a capability or option the graph does not offer. The refusal goes to the integrator, which returns it to the dispatch.

**The branches.** One node, **Parallel** (`branches`), runs every branch. Each branch has its own session, its own worktree and temporary branch from one recorded base, and the role, task and model policy of the capability it runs as. It does not take that capability's routes: a branch is a separate agent task, not a subgraph, and its result returns to the integrator with the others. Its model is the one its own class maps to for the agent that runs the graph, through **Model classes…**; no agent is switched. At most three run at once where the agent allows it; under an agent that runs one at a time in DSpatch, the same branches run one after another, and the result and each branch's record say so. A second visit, after the integrator sends the work back, makes a new round of branches beside the first round's, each with its own output and record.

**Messages.** The branches can send each other messages with `send_message`, read them with `check_messages` and acknowledge them with `acknowledge_message`. A message is delivered only when its recipient checks, so each branch is told to check before it starts, after a significant change and before it finishes; one that ends with messages still waiting is asked once, in the same session, to check them (DSP-227). Each branch is also told which other branches work beside it and on what, and to send a finding that another branch's task depends on as soon as it is established. Sent, delivered and acknowledged are recorded apart. A proposed change to a shared contract is a proposal: it is listed for the integrator and binds no one. A branch that cannot finish without such a decision does not wait for it and does not assume it; it finishes what it can and ends with an *Open decision* section, which the integrator returns for coordination.

**The integrator.** The **Integrator** (`integrator`, role `generic-integrator`) is given every branch's result, its ending, its open decisions, the open proposals and every message with its delivery. It checks each branch against the shared contracts, merges the temporary branches in the listed order, resolves conflicts and names each, and runs the checks that show the parts work together; a clean merge is not that evidence. It chooses `integrated` only when every branch finished and was combined and checked and no proposal is open; `rework`, with findings per branch, sends the branches back for another round; `return-to-lead` returns a failed or cancelled branch, an open contract decision or a split that has to change to the dispatch, naming where each branch's work is kept. A failed branch reaches the integrator by name, never the review as if the whole were done.

**Review of the whole.** The work goes on after the branches with the strongest review route any branch carried (the review choice is ordered and declares `joins: strongest`): if one branch needed the thorough route, the integrated work goes through design QA and the thorough review, never the standard one. The model class does not join (DSP-227): the integrator's model is its own explicit policy, which follows the class the dispatch chose for the subtask (medium when that is small), so a large branch does not by itself make the integration large. A graph that wants that gives its class choice `joins` as well. QA is given the integrator's result, and the review and the challenge follow on the route as for any other work.

**On the canvas.** The node shows how many branches its latest visit ran and each model class with its count (for example *2 branches: Small ×1 · Large ×1*), with a tag of their letters, never one class as if it applied to all of them. The Branches list and the branch output window give each branch's task, role, state, class and model, live output and saved result, and its messages with their delivery counts.

## Behaviour the run engine does not provide

These parts of the orchestration are carried by instructions or by ending the run, not enforced by DSpatch:

- **Model classes need a mapping to change the model.** Until the agent's classes are set in **Model classes…**, every class runs with the model chosen in the chat, and the editor's model line says so with a way into the setting. A class names the capacity asked for, not a guarantee of the model's.
- **A revisit may carry the earlier conversation.** A node keeps one agent session for the run. A revisit with the same model continues it on every agent, so the agent has its earlier visits' conversation in context: a rework round, and an escalated review or challenge whose two classes map to the same model (for example both set to *Use chat model*). With a different model, Claude switches the model in the same session (the earlier conversation stays in context) and the other agents open a new session for the visit (it has only its brief). Each visit's output is shown on its own, and the step output window and node panel say which of these happened; showing a visit apart does not make it an independent review of the earlier one. Before DSP-224 the large review and the full challenge were separate nodes with sessions of their own. (DSP-225, observed in the run engine and with simulated adapters; the session policy is unchanged.)
- **No pause for human authorization.** When Infrastructure needs a job approved, the job plan is reviewed and the run goes to wrap-up and reports. Approving and launching the job happens outside the run; a new run continues afterwards. The graph has no human step.
- **One slice at a time, unless the dispatch splits it.** Slices run one after another; within one slice, the dispatch may run independent parts as parallel branches (above). Subagent delegation is off unless the user authorizes it.
- **The integrator merges; DSpatch does not.** Merging, conflict resolution and the contract check are the integrator's instructions, not a check DSpatch makes. That the integrator does not report a failed branch as integrated is its instruction; DSpatch makes sure the failure and the branch's kept work reach it. Merging needs a clean working copy: with uncommitted changes to tracked files, the merge is refused and the integrator returns the work to the lead.
- **Parallel branches in this graph are not observed with a real provider.** They were run through the engine and the live executor with simulated adapters for Claude (two at once) and Cursor (one at a time), with real git worktrees. The fan-out itself, with two real Claude branches and a real integrator, was observed in DSP-227's coordination pilot on a small graph of its own (see `docs/loop/pilots/branch-messaging-pilot.md`); how many branches the other agents run at once is read from their integrations' code, not observed.
- **The carry-forward ledger is not verified.** The runner delivers the named results along each edge; that each reply carries the ledger is the agents' instruction, not a check.
- **Limits are bounds on routing, not a hard cap.** See the paragraph on the call limit above.
- **Not yet tried with a real provider.** Its integration was checked with simulated adapters for each agent and in the packaged application without a model call.
