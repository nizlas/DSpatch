# DSpatch 0.1.6

## Zoom, per window

- Every DSpatch window zooms on its own: the chat, the loop editor, review windows, code walks and the review's discussion. Ctrl and `+` (or `=`) enlarges, Ctrl and `-` reduces, Ctrl and `0` restores normal size; the keypad's `+`, `-` and `0` do the same, and the keys of the Swedish layout as well as the US one. Each press is one of VS Code's steps (20 % per level, between −8 and 8). The View menu has Zoom In, Zoom Out and Reset Zoom with the same keys.
- A press in a text field, a code view or the discussion changes the window and types nothing. Only the active window changes.
- Each window's level is remembered on this computer, in the client's own data (`window-zoom.json`), by what the window is for, not by its temporary id: a reopened window comes back at its size before it is drawn, and so does a window after a restart. Nothing is stored in the project, on a remote host or in a provider session; saved values are checked when read.
- The review's discussion follows its code window while docked; in a window of its own it has that window's own saved level, which docking neither changes nor forgets.

## Fixes

- **Starting the local host.** A start that loses the race for the host waits for the winner instead of reporting a failure; a start slower than its bound stops its own late host before reporting, so no host takes the data folder afterwards — on Linux as on Windows, where the Linux half of that wait was missing. On Windows the host is started holding none of the client's handles (the DevTools port stayed taken) and with every path as data, and concurrent starts over SSH to a Windows machine all reach their host.
- **Host identity.** A running-host record or claim counts only as the process it names: on Linux by the boot and the process's start, on Windows by a pipe only that process holds. Replace signals nothing it cannot confirm.
- **Copilot hooks.** A DSpatch tool whose pre hook failed is refused before it runs; only that call is refused, not the turn.
- **Chat.** An empty chat reopens normally instead of a resume error; a stopped turn reads the same live and after reopening; a conversation path that runs through a file reads as no file on Linux too, so what is wrong is reported at the save.
- **Loop runs.** A look at the working folders that missed something, or came late, is not taken for a command's moment or a finding.
- **Running from the repository.** `npm run dev` gives a current build identity and names an older running host as such; a development start can name an isolated profile and stops on any other.
- The decisions on hook failures and on the default loop are recorded as Niclas's confirmed decisions.
- **A window that stayed hidden on Linux.** The tagged 0.1.5 build was not published: its installed trial showed a window appearing only when something else asked its page for a frame, because a zoom level was set on the page before it had drawn. No zoom is set on a page that has not drawn yet; a restored level is applied by the page's own preload, as before, and only when it is not normal size.

## Linux download

Install `dspatch_0.1.6_amd64.deb` on Debian or Ubuntu x64. No separate Node, npm or host-package installation is required. Provider preparation and sign-in still take place where the work runs. The matching standalone host archive, its manifest and `SHA256SUMS` are also published.

No system service or login-time startup is installed. No Windows installer and no Windows host package are in this release: on Windows, DSpatch is run from the repository, and a Windows machine cannot be connected to over SSH from a released client.

## Verification

On Linux, through the repository's `linux-verify` workflow on GitHub's Ubuntu 24.04 runners at the release commit: the fast (1488 pass, 6 skipped), host (138 pass, 3 skipped), review (199 pass), chat (362 pass, 7 skipped), presentation (288 pass) and provider (170 pass) test groups, among them the POSIX host identity through `/proc`, Replace's refusal of an unconfirmed process, the stop of a late host and concurrent slow starts, run by a real `sh`. The zoom was tried in real Electron windows on an X display (Xvfb with a window manager) with the keys pressed through the X server: the US and Swedish layouts and the keypad, the View menu, three windows at different levels at once, the discussion docked and in its own window, a restart, and reset, and that the first window and a restored window are shown on their own: 57 checks (run 41798827206). The package workflow's installed trial gates the tagged build: the `.deb` in two clean containers with real Electron windows, real SSH and a simulated provider, the same standalone host through local close, reopen and SSH takeover; on this code it passed its 40 checks by hand before the tag (run 41798830717), and runs again on the tagged build. After publication, the published `.deb` is installed in a clean container and connected over real SSH, and an upgrade from the installed v0.1.4 is tried: the conversation, the agent and project choices and a loop of the person's own in the project must still be there, with the previous release's host met and ended by the new client. What those two showed is recorded below once they have run.

Not established here: a real provider's behaviour, Windows beyond running from the repository, and Niclas's own acceptance of the zoom's feel (DSP-167 stays in review). The windows were tried under Xvfb with a window manager, not on a real Linux desktop. Once in six runs the provider group's test of a stop during a Copilot job saw the job fail before the stop; the code there is unchanged since 0.1.4. The provider group ran with a stand-in model.
