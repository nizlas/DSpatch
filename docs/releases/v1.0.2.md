# DSpatch 1.0.2

A pre-release for **Linux x64** and **Windows x64** that makes preparing a Windows computer as an SSH host for a Linux client a few commands instead of a long guide. 1.0.0 stays the latest ordinary release.

## Preparing a Windows host with two scripts

- **`dspatch-prepare-windows-host.ps1`**, for Windows PowerShell 5.1 or PowerShell 7 as administrator. It installs OpenSSH Server if it is missing, creates its own firewall rule `DSpatch-SSH-In` that allows SSH only from the address or network given with `-AllowFrom` on the interface in use, puts the public key where sshd reads it for the account (`administrators_authorized_keys` for an administrator, the user's own `authorized_keys` otherwise) with permissions set by SID, and starts sshd with automatic start. It shows what it found and a plan of every change first and asks before changing anything; `-DryRun` stops after the plan. It reads `sshd_config` and never changes it, never changes the network profile, never restarts Windows (it says when a restart is needed), and stops when policy or the update source blocks it. Run again, it changes only what is not already in place. It prints the host key fingerprints and the `ssh` command for the client.
- **`dspatch-prepare-linux-client.sh`** finds your SSH public key, or creates an ed25519 key if you have none, never overwrites or prints a private key, and prints the exact Windows command with your key and this computer's address filled in.
- Both come with the client in `resources/bundled/remote-setup/` (on Linux `/opt/DSpatch/resources/bundled/remote-setup/`), are published with this release and listed in `SHA256SUMS`.

## Help

- *Help → Connect to a Windows Host over SSH…* now starts with the short way: the Linux helper, the Windows script, then the fingerprint check and Connect. The download address in it names this version. The manual steps are kept as reference, and troubleshooting has the script's stops and PowerShell's execution policy.
- **Save Windows script…** and **Save Linux helper…** at the top of that window save a copy of either script, for a USB stick or a share.
- Two corrections in the manual steps: an account's administrator membership is checked with `whoami /groups` and the SID `S-1-5-32-544` (also when it shows as *Group used for deny only*), not `IsInRole` in an ordinary PowerShell; and `administrators_authorized_keys` gets `icacls /inheritance:r /grant:r "*S-1-5-32-544:F" "*S-1-5-18:F"`, with a check that only those two entries remain.

## Install

- **Linux (Debian/Ubuntu x64):** `dspatch_1.0.2_amd64.deb`. Check it against `SHA256SUMS` and install with `sudo apt install ./dspatch_1.0.2_amd64.deb`.
- **Windows (x64):** `DSpatch-Setup-1.0.2.exe`, a per-user installer. It is not signed; see [INSTALL.md](../INSTALL.md#windows).
- `dspatch-prepare-windows-host.ps1`, `dspatch-prepare-linux-client.sh`, both host packages, `host-manifest.json` and `SHA256SUMS` are published with this release.

The host contract is unchanged from 1.0.1.

## Tried, and still to be tried

Tried by agents on Linux: the Linux helper in a temporary home folder (a new key, an existing key left byte for byte, a public key derived from a lone private key, no private key material in its output), static checks of the Windows script (every change only after the plan, `-DryRun` and confirmation; `sshd_config` only read; keys written as UTF-8 without a BOM; SIDs; no defaults), the staged file list, and the client build.

Tried on a real Windows 11 computer (Windows PowerShell 5.1.26100), read-only: the script parses without errors, and its `-DryRun`, with a throwaway test key, found the account as an administrator through `whoami /groups`, the interface, its network profile and the existing OpenSSH setup, chose `administrators_authorized_keys` from the default `sshd_config`, saw that file's permissions as already correct, planned two changes (its own firewall rule and the key), explained instead of disabling the broad `OpenSSH-Server-In-TCP` rule because SSH was already in use, and changed nothing (checked afterwards: no rule, no key).

Not yet tried:

- **the Windows script's system-changing path** (installing OpenSSH, creating the firewall rule, writing a key, setting permissions, starting sshd) **has not been run on any Windows computer**;
- the Help window's save actions in a real window;
- the setup on a work network with its own policies;
- the open points listed for 1.0.1.
