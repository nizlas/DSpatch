# DSpatch 1.1.0

An ordinary release for **Linux x64** and **Windows x64**, and the new latest release. It adds controlled parallelism to agent execution graphs, makes model choice and parallelism reusable sections a graph builder adds in the editor or through the chat, and carries what parallel branches find and leave open to the step that integrates them.

## Controlled parallelism in the generic development graph (DSP-226)

- **Tech Lead chooses.** The generic agent network's dispatch can answer `parallel` and split a subtask into two to six independent parts; dispatching one capability stays the usual way.
- **Each branch** runs as the capability its part names, with its own model class and review route, in its own session and its own git worktree from one recorded base. Overlapping write ownership and parts that depend on each other are refused before any branch starts.
- **An integrator** receives every branch's result and ending, merges the temporary branches, runs the checks of the whole, and sends it to the review route the strongest branch needed. A failed branch reaches it by name and is never reported as integrated.
- **On the canvas** the fan-out node shows a summary of its branches' classes (for example *S·M·L*), and the branch list shows each branch's task, role, class, model, output and messages. A revisit makes a new round, kept apart from the earlier one.

## Reusable model choice and parallel sections in the graph editor (DSP-227)

- **Choices made per task**, with nothing selected in the graph editor: add a model-class choice, a review-route choice or one of your own. Set the options and the criteria for each, the class each option means, the default, whether the options are ordered, what a missing or invalid value gives, which steps decide it and which steps' models follow it. The model of each class is still the agent's *Model classes* setting, never the graph's.
- **Parallel sections**: add one, or change it on the fan-out node. The settings cover the proposing step, the roles a branch may run as, each branch's model, concurrency and isolation, the integrator and its own explicit model policy, and where integrated, failed and undecided work goes. The proposing step's other outcomes stay its sequential path.
- **Generated instructions.** DSpatch writes the instructions for deciding a choice and for writing the split from these settings, and shows them in the node's message panel; no purpose or role has to carry the formats. Graphs from earlier versions load as before.
- **An example graph** of its own, *Workshop*, is in `docs/loop/examples/workshop`.

## Graph sections proposed in the chat (DSP-227)

The chat agent can add or change a choice or a parallel section from the same settings with `propose_graph_section`. Like any graph proposal it writes nothing until you apply it, and it is checked first.

## Messages and shared task context between branches (DSP-227, DSP-228)

- Each branch is told which other branches work beside it and on what, and to send a finding that another branch's task depends on as soon as it is established.
- A sent question is no reason to stop: a branch goes on with work that does not depend on the answer, checks its messages at natural boundaries rather than polling, never guesses an answer it needs, and never treats a proposed contract change as agreed.
- Sent, delivered and acknowledged are recorded apart. Acknowledged is the branch's own statement; what it changed is in its result and commit.

## Open decisions and blockers reach the integrator whole (DSP-228)

A branch that cannot go on ends with an *Open decision* or *Blocked* section. The integrator receives every such section quoted in full, even when the branch's reply is otherwise shortened, with the reminder that a branch ending finished its slice, not the task.

## Install

- **Linux (Debian/Ubuntu x64):** `dspatch_1.1.0_amd64.deb`. Check it against `SHA256SUMS` and install it with `sudo apt install ./dspatch_1.1.0_amd64.deb`. It carries both host packages, so it can install a host on a Linux or a Windows computer.
- **Windows (x64):** `DSpatch-Setup-1.1.0.exe`, a per-user installer. It is not signed; see [INSTALL.md](../INSTALL.md#windows).
- **After an upgrade,** a host started by the earlier version keeps running. The window reads *Restart needed to finish updating*, and **Restart host** starts this version's host with the data kept.

## Verified, and known limits

**Verified:**
- Targeted tests of the engine, the sections, the generated instructions, the slice rules, the mailbox, the reminder and the transfer of open decisions, with simulated adapters and real git worktrees.
- The type check and the build.
- A window trial in an isolated profile with a recorded scripted run, covering the editor's section forms, an edit saved to file, the generated instructions, the branches' classes and models, and visits kept apart.
- **Real collaboration trials with Claude**, through DSpatch's run engine, in a small synthetic repository: twelve runs with two parallel branches and a real integrator. They showed that branches overlap in time, that messages are delivered and used, and that a branch with an open question keeps working. The report is `docs/loop/pilots/branch-messaging-pilot.md`.

**Known limits:**
- **No trials with real Copilot or Cursor providers.** How many branches they run at once (Copilot three, Cursor one, one after another) is read from their integrations' code.
- **Messages are fetched by the recipient.** A message is delivered only when the receiving branch checks. A branch that ends with messages waiting gets one bounded reminder in the same session. There is no push delivery. In the trials the reminder, not a mid-work check, delivered most replies.
- **No general gain in quality or speed has been shown.** In the trials the clearest improvement came from branches knowing each other's tasks. Messages changed the receiving branch's work in several runs, but it usually found the same thing on its own, and messaging cost extra turns and tokens.
- **A parallel branch is an agent task, not a full subgraph.** It borrows a step's role, purpose, requirements and model policy, not its routes or continuations. Nested subgraphs are not run.
- The integrator's merge and its checks are its instructions; DSpatch makes sure every result, message and open decision reaches it, but does not merge.
- **Not yet tried for this release:** a branch's live output in the window during a live run, and Windows.
