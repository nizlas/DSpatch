# DSpatch 0.1.13

A Linux-only pre-release for evaluating the explanation instructions aligned with the code-walk reference ([docs/CODE_WALK_UNDERSTANDING_AND_PROFILES.md](../CODE_WALK_UNDERSTANDING_AND_PROFILES.md), DSP-188). No Windows installer or Windows host package is published; the Windows work (DSP-182) is still open.

## Step explanations (DSP-188)

- **One task, three readers.** Every profile is given the same explanation task: say what the code does here and why it matters for the change, how it connects to what the reader has seen and will see, and what the reader must understand to judge it; read the code it rests on first; add understanding beyond what the lines say; keep what the code shows apart from interpretation. Each profile adds only a short description of its reader. Essentials is for an experienced developer who wants quick orientation, Standard for a developer who knows programming but not this code, Teacher for a reader who may not know the language, library or mechanism.
- **No quotas.** No profile is told how many sentences to write or how many identifiers to name. The scope follows the code and the reader: a simple step is said in a few words in every profile, a step where several mechanisms interact takes the room understanding needs.
- **Transitions.** A step is written relative to the walk: how this code was reached and what the caller needs from it, what happens on a return, that an alternative outcome goes back to the branch point rather than continuing one run, and for a worker or callback what starts it and which execution context the walk now follows. A teaching order that differs from the execution order says so.
- **Show more** carries the deepening only, in the same manner as the first part: the mechanisms behind what it says, special cases that change the outcome, longer evidence and more references.
- Instruction version 7. Explanations written with earlier versions stay viewable in their history with their own version.

## Preparing walks (DSP-188)

- The walk generator is asked to treat alternative branches as alternative paths that return to the branch point, to say what starts a worker or callback and which execution context the walk follows, and to say when the teaching order differs from the execution order. These are judgment, not mandatory items: the structural checks force no step per branch and no fixed shape.
- Every central mechanism a step shows is explained in that step, at the reader's level; naming a function or showing its lines is not treating it.

Everything decided in 0.1.12 stands: step explanations apart from the discussion, one code place per step, references that lead somewhere, reviews as instances.

## Install or upgrade

Install `dspatch_0.1.13_amd64.deb` on Debian or Ubuntu x64 (`sudo apt install ./dspatch_0.1.13_amd64.deb`). Installing over an earlier version keeps `~/.config/DSpatch`.

0.1.13 speaks the same host contract as 0.1.12. A host that 0.1.12 started keeps running through the upgrade; the new window connects to it and says that a restart is needed to finish updating, so press **Restart host** there before preparing walks: walks are prepared on the host, and the old host still carries the earlier instructions until it is restarted. Step explanations come from the window and use the new instructions at once. A host on a machine you connect to over SSH is updated from this release's host package.

`dspatch-host-0.1.13-<commit>-linux-x64.tar.gz`, `host-manifest.json` and `SHA256SUMS` are published with this release.

## Verification

Checked before publication (details in DSP-188): type check and the review and presentation test groups on Windows, `linux-verify` on Linux; the walk and profile window trials with the simulated provider; a generated walk read through DSpatch's own reader and structural checks.

The instructions were judged on actually generated text: a Claude model outside DSpatch's providers answered DSpatch's exact prompts for two synthetic cases (a C++ work queue with a worker thread, lost wake-ups and a shared handle; a TypeScript connection with retries, two outcomes and a deferred callback), in all three profiles and with *Explain this* on the same lines, and a second model judged the texts against the code. The texts and the judgment were given to Niclas with this release.

Not established:

- What your provider writes with these instructions on real code. The model-written texts show what the instructions ask for and what a capable model makes of them; they are not evidence of how another model behaves.
- External context (a dependency read as context) in generated explanations: the synthetic cases have none, so how the texts convey and link it was not judged in this round.
- Windows, other distributions than Ubuntu and Debian, and arm64.
