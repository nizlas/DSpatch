# DSpatch 0.1.14

A Linux-only pre-release for evaluating a first version of code walks prepared by a planner, a writer and a reviewer instead of one call (DSP-189). No Windows installer or Windows host package is published; the Windows work (DSP-182) is still open.

## Preparing walks with the planner, writer and reviewer (DSP-189)

- **A choice in the preparation picker.** *Prepare code walks* now offers **Preparation: One call** (as before, the default) or **Planner, writer and reviewer (evaluation)**. The choice is the computer's and is remembered.
- **What the loop does.** The planner reads the two revisions and plans the walks: purpose, steps, one code place each, how each step is reached, and a brief for the writer. The writer explains every step in the chosen profile, one step per call in its own session, with the whole plan and its own reading of the code. The reviewer reads the finished walks as you will, checks them against the code and either accepts them or names concrete shortcomings. Structural findings go back to the planner (and the affected steps are written again), explanation findings to the writer; at most one such round. The reviewer's second visit is the final assessment and asks for nothing more; what still falls short is on record.
- **The same walks, the same reading.** Both preparations write the same walk definition, so a loop-prepared walk opens and reads like any other, in the chosen profile. Step and Discussion are untouched: nothing of the loop's exchanges reaches them.
- **The trace, on request.** After the loop has run, the review window shows one line under the preparation area: how it ended, whether a correction round ran, how many provider turns it took and how long, and what the provider reported about usage (unknown when it reported nothing). Open it for the reviewer's verdict and findings, the final assessment, the engine's journal and, under a control of its own, every prompt and answer whole. The reviewer is an agent: its acceptance approves nothing of the code.
- **Stopping and failing.** Stop ends the run at its current turn and starts nothing more; a provider failure ends the job without a resend; a late answer never reaches another review or recreates a deleted one.
- **How it is built.** The loop is a DSpatch loop graph, `docs/loop/graphs/dspatch-walk-loop.graph.json`, with roles in `docs/loop/roles/review/`, walked by the same run engine as the chat loop; the graph opens in the graph editor like any other. The run's record is kept with the review in the loop's record format.

Everything decided in 0.1.13 stands: one explanation task and three readers, no quotas, transitions as judgment.

## Install or upgrade

Install `dspatch_0.1.14_amd64.deb` on Debian or Ubuntu x64 (`sudo apt install ./dspatch_0.1.14_amd64.deb`). Installing over an earlier version keeps `~/.config/DSpatch`.

0.1.14 speaks the same host contract as 0.1.12 and 0.1.13. A host that an earlier version started keeps running through the upgrade; the new window connects to it and says that a restart is needed to finish updating. **Press Restart host before preparing walks**: walks are prepared on the host, and an old host neither knows the loop nor carries its drawing and roles; the one-call preparation on an old host would also use the earlier instructions. A host on a machine you connect to over SSH is updated from this release's host package.

`dspatch-host-0.1.14-<commit>-linux-x64.tar.gz`, `host-manifest.json` and `SHA256SUMS` are published with this release.

## Verification

Checked before publication (details in DSP-189): type check; the review test group (the loop's routing with a scripted session, the loop through the host's job service with the simulated provider, the further synthetic cases, the stop, the deleted review); `linux-verify` on Linux, with the new walk loop window trial beside the profile trial (the choice in the picker, the job line, the walks opening, the trace on request, the record on disk); the published package in clean containers and an upgrade from the previous release.

The loop was also run through the real product path with a file-backed stand-in for the provider, answered by a Claude model outside DSpatch's providers, on synthetic cases, beside today's one call on the same code and profile; the exact prompts, answers, plans, findings and definitions are kept with DSP-189 and given to Niclas.

Not established:

- What your provider writes in the three roles on real code, and what the loop adds there. The stand-in run shows what the prompts ask for and what one capable model makes of them on the product's own path; it is not evidence of another model's behaviour, and the comparison on real code is yours to judge.
- The extra wait and usage with a real provider: the stand-in's times are a model outside DSpatch answering files, and no usage was reported.
- Windows, other distributions than Ubuntu and Debian, and arm64.
