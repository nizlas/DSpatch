# DSpatch 0.1.15

A Linux-only pre-release that keeps the diff view free of generation details, separates the profile a walk is read in from the settings it was prepared with, and adds a window of its own for following a walk preparation through the planner, writer and reviewer (DSP-190). No Windows installer or Windows host package is published; the Windows work (DSP-182) is still open.

## Two faults of 0.1.14 corrected

- **The text above the file list.** After a loop-prepared walk, the diff view showed *Prepared through the planner, writer and reviewer loop: …* followed by hundreds of token values. The line wrote every usage reading the provider reported into the heading of its details element, and a real provider reports usage per model call. The trace is gone from the diff view altogether: one short line says how the walks were prepared and opens the run view, and nothing of the run (verdicts, journal, usage, prompts, answers) sits in the diff view, in Step or in Discussion.
- **"Prepared with earlier settings" after changing the reading profile.** Choosing Essentials in the walk window also set the computer's default profile, which the diff view compared with the profile the walks were prepared in; the walk window's own Step panel compared the reading profile with it directly. Changing the profile a walk is read in is the person's choice per walk: it shows a saved explanation or asks for the missing one for the current step, and by itself marks nothing out of date, asks for no new preparation, starts no loop and changes no places, order, coverage or decision. The notice is said only for a real difference of DSpatch's instruction version; the profile, instruction version, provider, model and method a walk was prepared with stay as provenance and are shown in the run view and with the walk's own text.

## Follow preparation (DSP-190)

- **A window of its own.** *Follow preparation* on the running job line and on the preparation line of a loop-prepared walk opens it, during the run and afterwards. Closing it stops nothing; opening or reopening it starts no call and no run. One window per preparation; a second press brings it to the front.
- **The loop's drawing, as the graph editor draws it.** The same canvas, node shapes, run states, ending tick and motion, in a view mode: zoom, panning by dragging, a click on a node to read its latest visit, and no palette, inspector or saving. The marks are a reading of the engine's own journal: the actual path, the correction round if one ran, where the run ended.
- **The activity beside it, as reported.** Each node visit and each provider turn, in order: the turn DSpatch sent and why (which step, how many of how many), streamed reply text, reasoning text where the provider exposes it (labelled as exposed reasoning), tool calls with what they read and whether they ran, commands with their output where the provider reported it, usage readings, DSpatch's own status (the mechanical checks, a repair asked for, the outcome declared), the reviewer's verdict and findings, and how the turn ended. Rows are short and expand to the whole content with its formatting. The panel follows the active node; an earlier visit can be read while the run goes on, without the list moving under the reader, and *Back to live* returns. There is no field to type into.
- **A compact summary.** Turns, time, the correction round and the ending; usage summed only per provider source whose meaning is known (Copilot per model call, Claude and Cursor per turn, field by field; provider totals shown apart; a reading without a known field counted, not added), unknown as unknown, never zero for silence; the details open apart. *Every prompt and answer of the run* remains readable on request.
- **Stop.** The job's own Stop, which cancels the job and the active provider turn; a provider failure ends the run without a resend; a deleted review closes its run view and gets nothing recreated.
- **Kept with the run.** The activity (reasoning within a bound per turn, everything else as it came; the reply text is on the record's own reply lines) and the drawing the run walked are written beside the record, so a finished run is inspected from its files. A run recorded by 0.1.14 shows its turns with every prompt and answer, its journal and its verdicts, and says that streamed text, tool calls and usage were not kept for it.

## Install or upgrade

Install `dspatch_0.1.15_amd64.deb` on Debian or Ubuntu x64 (`sudo apt install ./dspatch_0.1.15_amd64.deb`). Installing over an earlier version keeps `~/.config/DSpatch`.

0.1.15 adds a host method (the run as it stands, for the window that follows it), so its host contract differs from 0.1.14's. A host that 0.1.14 started and that a closed window left running cannot serve this window: at start DSpatch says that a host of another version is running here over the same work and asks **Stop it and continue** or **Quit DSpatch**. Stopping it ends any work still running there, with that work's outcome unknown; nothing else is lost, and this release's host then starts. There is no Restart host step. Walks saved by earlier releases open as before; to see the run view with its activity, prepare walks with the loop in a new review.

`dspatch-host-0.1.15-<commit>-linux-x64.tar.gz`, `host-manifest.json` and `SHA256SUMS` are published with this release.

## Verification

Checked before publication (details in DSP-190): type check; the review test group (the activity model and the usage summary, the host's follow state over a scripted run with the files read back, the loop through the host's job service with the run events and the snapshot, nothing sent for a deleted review); the loop and provider groups; `linux-verify` on Linux with the walk loop trial and the new follow preparation trial in real windows (the run view opened while the planner works; the writer, the reviewer, a correction round and the final assessment with real stream events; rows expanded; an earlier visit read during the run and back to live; closed and reopened without a stop, a double or an extra call; the finished run reopened; the diff view free of generation details; Standard to Essentials and back with one explanation call and no staleness notice; a second review of the same pair followed on its own and stopped; a provider failure; a review deleted while its loop ran); the published package in clean containers and an upgrade from the previous release.

Not established:

- Anything with a real provider: the trials use the simulated provider, which reports usage and reasoning only when asked to. What Claude, Copilot or Cursor actually stream in a walk loop (reasoning present or absent, usage fields, tool result detail) is what the adapters already normalise and has not been observed in this view with a real model.
- A command's output in the activity panel, which the simulated analysis tasks run none of: covered by the host's handling of a reported command, not seen in a window.
- Windows, other distributions than Ubuntu and Debian, and arm64.
